### Работа в команде (обязательно)

Сессия (pod) лабы живёт, пока её явно не закроют (выход/смена устройства её не закрывают). У каждого человека **свой** `*_pc`
(`.pnet-account`); к открытой сессии лабы другие аккаунты **присоединяются** (Join, `factory/join`) и работают с теми же узлами
(проверено 2026-10-23: serj_pc в сессии vlad_pc). `tools/pnet-mcp.py` нужен для этого: он не даёт MCP при открытии лабы уйти
из присоединённой сессии в свой пустой pod (штатный MCP делает `factory/create`). Общее для всех pod — только топология
и startup-config IOL в `.unl` и опубликованные образы qemu-узлов `<шаблон>-<лаба>-<узел>-vN`. Лабам на одних IOL образы не нужны.
`H="<venv MCP>/bin/python tools/pnet-helper.py"`:

Креды всех `*_pc` — `mcp-creds.json` в корне (в `.gitignore`, шаблон `mcp-creds.example.json`; **репо публичный** —
пароли не выводить, не копировать в другие файлы и не коммитить); MCP в `.mcp.json` запускается через
`tools/pnet-mcp.py` под аккаунтом из `.pnet-account`.
1. **Открыть:** `$H sessions` (или `status LAB`). У лабы есть сессия с запущенными узлами → `$H join LAB` (несколько — спросить
   пользователя, к какой); нет → обычный `get_lab`/`start_all` через MCP (нет лабы — `create_lab`). Аккаунт сменить: `$H use <акк>` + **/mcp → Reconnect**.
2. **Работать** через MCP, как ниже.
3. **Сохранить:** `write memory` на IOL → `export_config` (0) → `download_lab` в `<лаба>/stand/`. Сессию **не закрывать** —
   к ней присоединяются остальные. В присоединённой сессии могут одновременно работать другие — не трогать то, что правят они.
4. **Опубликовать** (только по запросу; узлы сессии выключаются — предупредить присоединённых): на изменённых qemu-узлах выключить ОС (`poweroff` / `Stop-Computer`), убедиться, что узел остановлен →
   `$H snapshot LAB NODE` (root SSH только по ключу — у кого его нет, `ssh-copy-id root@100.100.57.19`; узел .unl переводится на новый образ, хранятся 2 версии) →
   снова запустить свои узлы → проверка на клоне лабы (`clone_lab` → `start_all` → проверки → `stop_lab` + `delete_lab` клона;
   `delete_lab` рушит **текущую** привязанную сессию — перед ним обращаться к клону, не к рабочей лабе) → `download_lab` → git commit.
   Образы большие (Windows/Kali ≈ 12–13 ГБ); перед публикацией смотреть `df -h /` на хосте.
- `$H sessions` — кто где открыт. Чужие сессии не закрывать; `stop_lab` (рушит **все** сессии лабы), `wipe_node`, `delete_*` — только по прямой просьбе.
- Перед `snapshot` проверить, что в своём pod узел реально настроен (а не свежий из образа) — снимок перезапишет общее состояние.
- Хост: оверлеи узлов — `/opt/unetlab/tmp/<id сессии лабы>/<поле session узла>/*.qcow2`, образы — `/opt/unetlab/addons/qemu/`.
  `/opt/unetlab/tmp` — на корневом ext4, при загрузке хоста не чистится (проверено 2026-10-23): после выключения хоста сессии
  и диски узлов остаются, узлы надо запустить заново. Перед выключением хоста: `write memory` + `export_config`, на qemu-узлах
  выключить ОС; VPCS-адреса задать заново.
  Базовые образы шаблонов (`linux-ubuntu-server-22.04` и т. п.) не удалять: на них стоят чужие лабы и оверлеи живых pod.
- MAC узлов зашиты в `.unl` — одна лаба в двух pod даёт одинаковые MAC/IP в облаке управления (pnet0); не держать две копии
  с запущенными узлами, у которых есть облако.

- **Одна сессия на аккаунт.** Если одновременно открыт другой клиент (Claude/Codex) с тем же MCP-аккаунтом — вы выбиваете друг друга. Работай из одного клиента.
- **Свой экземпляр лабы.** У аккаунта у каждой лабы свой pod: изменения в консолях видны только в нём, пока не опубликованы. Пользователь смотрит своим веб-аккаунтом через Join (Running Labs).
- **Перед изменениями** — `get_lab`, сверить id нод и интерфейсы. IOL-индексы: e0/0=0, e0/1=16, e0/2=32, e0/3=48, e1/0=1, e1/1=17 и т. д. (можно передавать имя `e0/1`).
- **Консоль теряет символы на длинных пачках.** `send_console` — блоками по 5–10 строк; после блока проверять `show run | include ...` через `read_console`.
- **Новые IOL-ноды** при первом старте висят в `initial configuration dialog` — сначала отправить `no`.
- **`read_console` возвращает скриншот**, не текст:
  - VPCS: начинать список с двух пустых строк и давать **одну** команду с выводом (`ping 8.8.8.8 -c 2`, `trace X -m 5`) — тогда вывод виден;
    при повторном подключении экран VPCS часто пустой или с обрывком команды — повторить вызов; если не выходит, проверять по счётчикам на IOL
    (`show ip access-lists`, `show ip nat translations`, `show ip dhcp binding`, ping с IOL);
  - пустой экран IOL — повторить с пустыми строками в начале и конце списка команд;
  - если у пользователя пустая telnet-консоль VPCS после работы MCP с этой нодой — подождать пару минут, консоль
    освобождается сама (2026-10-16); ноду не перезапускать. Пока пользователь работает в консолях — в них не заходить;
  - для отчёта вывод переписывать со скриншота дословно; если не читается — попросить пользователя скопировать вывод из консоли в браузере.
- **IOL L2:** перед `vlan N` нужен `vtp mode transparent`, иначе VLAN не попадут в конфиг. **VPCS** игнорирует startup-config — IP только через консоль (`ip ...`, `save`).
- **VPCS `ip dhcp`** — отдельным вызовом `send_console` (после `clear ip` в той же пачке теряется). Результат проверять на сервере (`show ip dhcp binding`)
  и на коммутаторе доступа (`show ip dhcp snooping binding`).
- **Консоль IOL после простоя выходит в `>`** — каждый блок начинать с `""`, `enable`. Иначе `clear ...`/`configure terminal` молча не выполняются.
- **Известные баги IOL L2 (15.2) — учитывать при проектировании:**
  - L3-коммутатор (SVI + маршрутизация между VLAN): `no ip cef`, иначе транзит между VLAN одного коммутатора теряется;
  - DHCP Snooping при аплинках доступа в Port-channel: один VLAN не должен проверяться на двух коммутаторах доступа — DHCP идёт мимо
    STP-блокировки, петля, кончается память. Каждому ASW — только VLAN его хостов;
  - IP Source Guard ломает DHCP-хостов; sticky Port Security ломается, т. к. VPCS меняют MAC при пересоздании pod;
  - `interface range` по нескольким Port-channel может уронить ноду — настраивать по одному.
- **qemu-ноды (pfSense и т. п.):** MCP `add_node` создаёт их без опций шаблона (qemu_arch/nic/options, config_script) —
  не стартуют и оставляют процессы-сироты qemu на сервере, `connect_nodes` к облаку не умеет. Вместо этого —
  `tools/pnet-helper.py` (python из venv MCP, логин как у MCP): `add-qemu` (с опциями шаблона), `add-cloud`, `connect`,
  `type`/`keys`/`shot` для VNC-консолей с правильным Shift, `push` — файл на Linux-узел с проверкой md5 (telnet быстро,
  VNC — `--key-delay 0.05`). Его логин выбивает сессию MCP — MCP перелогинивается сам. pfSense: консоль только VNC, через VNC теряется Shift и каждая строка даёт лишний Enter;
  `export_config` не работает. Настройка — через веб-интерфейс по сети управления (облако pnet0 = VMnet8 192.168.226.0/24 хоста),
  скрипты `BKS/lab1/tools/pfsense-gui.py` (backup/restore config.xml) и `pfsense-config.py`. В окружении есть прокси — curl с `--noproxy '*'`.
- **Здоровье нод:** зависшая/упавшая IOL — `get_node_status`; память — `show memory statistics | include Proc` (норма ~55 МБ used).
  Перезапуск ноды — `stop_node` + `start_node` (разрешено). После перезапуска коммутатора доступа привязки snooping пропадают — повторить `ip dhcp` на его хостах.
- **Сохранение:** после изменений `write memory` на устройстве + `export_config` (node_id=0). Проверка — `get_node_config`. Флаг загрузки startup-config (`config`) MCP менять не умеет: если у нод `config: 0`, попросить пользователя включить его в веб-морде.
- **Не вызывать без прямой просьбы:** `stop_lab`, `delete_lab`, `wipe_node`, `delete_node` — они уничтожают состояние (`stop_lab` — сразу всех сессий лабы).
- **Таймауты.** Если MCP перестал отвечать — скорее всего, уснул хост PNETLab или пропала сеть (Tailscale). Не повторять команды вслепую: сначала `list_running_labs`, потом проверить, что успело примениться.

## Автосборка отчёта по лабе

Когда просят «сделай отчёт по лабе N» / «оформи лабу <имя в PNETLab>»:

1. Если папки лабы нет — `./new-lab.sh labN` (или `<предмет>/labN`).
2. Через MCP найти лабу (`list_labs`, `get_lab`): узлы, линки, сети.
3. Конфиги: `export_config` (node_id=0), затем `get_node_config` по каждому настраиваемому узлу →
   `labN/configs/<узел>.txt` (только итоговый конфиг; убрать пустые `!`, баннеры и служебные строки PNET вроде `no shutdown` на неиспользуемых портах).
   Быстрее для всех IOL сразу: `download_lab` → распаковать zip во временную папку → `python tools/extract-configs.py <лаба.unl> labN/configs`.
4. Проверки: если лаба запущена — `send_console` + `read_console` с нужными
   show/ping/traceroute → `labN/outputs/<узел>-<что>.txt` (вывод переписать со скриншота дословно). Если не запущена — спросить,
   запускать ли (`start_all`), не запускать самовольно.
5. Топология: скриншот схемы через MCP не получить — оставить заглушку
   `img/topology.png` и попросить пользователя вставить скрин из веб-интерфейса,
   либо нарисовать схему прямо в typst по данным `get_lab`.
6. Заполнить `labN/main.typ`: номер, тему, дисциплину, преподавателя (спросить, если неизвестно),
   разделы «Цель работы», «Задание» (из текста задания, если дан), «Ход работы»
   (топология → адресация таблицей → настройка по устройствам → проверка), «Заключение».
   Каждый листинг/рисунок — с меткой и ссылкой на него в тексте.
7. Собрать `typst compile labN/main.typ`, открыть PDF и проверить глазами.
   На Windows шаблон не установлен (install.sh — для macOS/Linux): скопировать `mephi-labs/` в `<dir>/local/mephi-lab/0.1.0/`
   и собирать `typst compile --package-path <dir> --font-path mephi-labs/fonts labN/main.typ`.

### Завершение работы со стендом

- После итоговых изменений: `write memory` + `export_config` (0) + `download_lab` в `labN/stand/`. Хранить **одну** актуальную
  выгрузку, старые удалять; имя выгрузки обновить в `stand/README.md`. `configs/` пересобрать из неё.
- `commands/` держать в итоговом состоянии: если настройку потом заменили (sticky → без sticky и т. п.), править исходный файл,
  а не копить файлы-исправления. Эксперименты, после которых всё откатили, в `commands/`/`outputs/` не оставлять.
- Инциденты эмулятора и эксперименты по ним — в отчёт только если пользователь согласен; итоговые новые настройки — в отчёт всегда
  (нейтрально, как часть проекта). Факты для себя — в `AGENTS.md` лабы.

### Листинги по ходу работы на стенде

Новые листинги (введённые команды, выводы проверок) сразу вставлять в `main.typ` в подходящий раздел
как сырой `raw`-блок с подписью и меткой. Текст вокруг не вылизывать. Формализация (описание, ссылки, порядок,
чистка) — одним проходом в самом конце работы над лабой. Файлы в `commands/` / `outputs/` по-прежнему вести.

Не трогать `mephi-labs/` без явной просьбы — он общий для всех отчётов.

## Единые инструкции для ИИ-ассистентов

- `AGENTS.md` — единый источник правил для любой модели и клиента. В корне — общие правила, в папке лабы —
  её состояние, решения и журнал. Перед работой читать оба файла целиком. Локальные уточнения относятся к своей лабе;
  прямые указания пользователя имеют приоритет. Новые подтверждённые факты записывать с датой в `AGENTS.md` лабы.
- `CLAUDE.md` — только совместимый указатель на соседний `AGENTS.md`; не хранить в нём отдельные правила.
  В клиенте без автоматической поддержки этих файлов явно прочитать корневой и локальный `AGENTS.md`.
  Смена модели не меняет принятых решений, ограничений и порядка сохранения стенда.
- В старых журналах есть незакрытые чекбоксы и ранние планы, уже выполненные или заменённые поздними записями.
  Сопоставлять даты, итоговый `main.typ`, `stand/README.md` и артефакты; не повторять работу только из-за старого `[ ]`.
  Состояние живой лабы проверять отдельно перед работой: записи 2026-10-16–24 не подтверждают её текущее состояние.
- Карта проекта: `HUMAN.md`; командная работа: `TEAM.md`; сценарии защиты: `<лаба>/demo-checks.md`.
  `BKS/lab1` — завершённая сеть ГО/филиала, `BKS/lab2` — отдельный стенд Ubuntu-МЭ (вариант 6), `SA/` пока без лаб.
- Конфигурация MCP для Codex лежит в `.codex/config.toml`; для Claude Code — в `.mcp.json`. Обе запускают
  `sh tools/pnet-mcp.sh`. Не переносить команды настройки Claude CLI в Codex простой заменой имени.
  Сначала проверить доступные инструменты текущей сессии; отсутствие Dropbox-коннектора не означает отсутствие методички:
  проверить локальную `preamble/`. Сам аудит репозитория не требует входа в PNETLab или консоли устройств.
- Сборка существующих отчётов из корня: `make BKS/lab1`, `make BKS/lab2`; просмотр изменений: `git diff --check`.
  После правок только Markdown пересобирать отчёты не требуется. После правок Typst нужна сборка и визуальная проверка PDF.
- Сохранять чужие незакоммиченные изменения. Не добавлять все файлы через `git add .`; перед коммитом проверить список
  файлов и отсутствие учётных данных MCP. Не менять `.pnet-account` и конфигурацию подключения в рамках обычной правки отчёта.
