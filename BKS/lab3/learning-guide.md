## 1. Какую задачу мы решали

У компании есть головной офис и удалённые площадки. Сотруднику в филиале нужно открыть внутренний сайт головного офиса. Между площадками находится чужая сеть — например, сеть интернет-провайдера.

Нам нужно решить несколько разных задач:

1. Объяснить компьютерам, куда отправлять пакеты до удалённой сети.
2. Перенести эти пакеты между площадками.
3. Защитить содержимое от чтения и незаметной подмены по дороге.
4. Разрешить только предусмотренные обращения.
5. Автоматически запускать всё после перезагрузки.
6. Проверить не только успешный запрос, но и поведение при отказе защиты.

Для этого недостаточно просто «включить VPN». В нашей лабе каждая задача решается отдельным механизмом.

| Задача | Что у нас её решает |
|---|---|
| Перенести пакеты между сетями | GRE-туннель |
| Защитить GRE на внешнем канале | IPsec |
| Договориться о ключах IPsec | IKEv2 в strongSwan |
| Автоматически узнать удалённые сети | OSPF в FRRouting |
| Ограничить разрешённые пакеты | Межсетевой экран iptables |
| Дать отдельный доступ к одному сервису через посредников | Каскад Xray |
| Запустить всё при загрузке ОС | systemd |
| Показать, что сервер доступен | Тестовый HTTP-сервис |

Запомни основную цепочку: **маршрут выбирает путь, туннель переносит пакет, шифрование защищает содержимое, фильтрация решает, можно ли его пропустить**.

## 2. Что спроектировано, а что реально собрано

В работе есть два масштаба.

### 2.1. Архитектурный проект

По варианту предусмотрены головной офис, два центра обработки данных и три вида удалённых площадок:

- 20 ПВЗ, то есть пунктов выдачи заказов, с оптикой или LTE;
- лаборатория в соседнем здании;
- подрядчик, которому нужен только один внутренний веб-сервис.

Для ПВЗ выбрали SD-WAN. Для лаборатории — направленный радиомост. Для подрядчика — ограниченный прикладной доступ через защищённый входной прокси. Два ЦОД нужны в проекте для резервирования.

Это проектные решения. Мы не разворачивали двадцать ПВЗ, контроллер SD-WAN, второй ЦОД или физические антенны.

### 2.2. Практический стенд

В PNETLab создали отдельную лабораторию с пятью виртуальными машинами Ubuntu Server 22.04:

| Узел | Расшифровка имени | Роль |
|---|---|---|
| `BR-CLIENT` | Branch Client | Компьютер сотрудника филиала |
| `BR-GW` | Branch Gateway | Маршрутизатор филиала |
| `HQ-GW` | Headquarters Gateway | Маршрутизатор головного офиса |
| `HQ-SRV` | Headquarters Server | Внутренний веб-сервер |
| `XRAY-RELAY` | Xray Relay | Промежуточный прокси |

PNETLab запускает виртуальные машины и соединяет их виртуальными сетями. Ubuntu внутри каждой машины работает как обычная ОС. GRE, IPsec, OSPF и firewall настраиваются уже в этих ОС.

Внешний канал в стенде — общий изолированный Ethernet-сегмент. Он изображает сеть оператора, но не моделирует всю сложность настоящего интернета.

## 3. Минимальная сетевая база

### 3.1. IP-адрес и подсеть

IP-адрес — адрес сетевого интерфейса. У одной машины может быть несколько интерфейсов и несколько адресов.

У клиента филиала адрес `10.2.20.42/24`. Часть `/24` задаёт размер подсети: первые 24 бита адреса обозначают сеть. В нашем случае это сеть `10.2.20.0/24`, маска `255.255.255.0`.

Для обычной такой подсети:

- `10.2.20.0` — адрес сети;
- `10.2.20.255` — широковещательный адрес;
- адреса `.1`–`.254` могут использоваться узлами.

Сервер имеет адрес `10.1.50.10/26`. Его сеть — `10.1.50.0/26`, маска `255.255.255.192`, обычные адреса узлов `.1`–`.62`. Клиент и сервер находятся в разных подсетях: нужен маршрутизатор.

Суффикс `/32` в правиле означает ровно один IPv4-адрес. Поэтому `10.1.50.10/32` ограничивает доступ одним сервером, а не всей серверной сетью.

### 3.2. LAN, WAN и сеть управления

**LAN — Local Area Network:** локальная сеть площадки. У нас LAN филиала — `10.2.20.0/24`, серверная LAN офиса — `10.1.50.0/26`.

**WAN — Wide Area Network:** сеть, через которую соединяются площадки. В стенде это `203.0.113.0/24`. Этот диапазон предназначен для примеров в документации; здесь он используется как адресация изолированного виртуального WAN, а не как реально выделенные публичные адреса.

**Сеть управления** — отдельный путь для администрирования: SSH, установка пакетов и обслуживание. У нас это `192.168.15.0/24`. Через неё можно управлять машинами, но тест межофисной связи должен идти через настроенные шлюзы и туннель.

Это важно: если проверочный запрос случайно прошёл по служебной сети, он ничего не доказал о VPN.

### 3.3. Шлюз и маршрут

Шлюз — машина, которая пересылает пакеты между сетями. В нашей лабе эту роль выполняют Linux-машины `BR-GW` и `HQ-GW`.

Маршрут — запись вида «для этой сети отправлять пакеты через такого соседа и такой интерфейс».

Например, клиент знает:

```text
До 10.1.0.0/16 идти через 10.2.20.1.
```

Адрес `10.2.20.1` — его локальный шлюз `BR-GW`. До этого соседа клиент может добраться по своей LAN. Дальнейшую доставку организует шлюз.

Если подходят несколько маршрутов, обычно выбирается наиболее конкретная подсеть: например, `/24` конкретнее `/16`, а обе конкретнее маршрута по умолчанию `/0`.

У клиента default route направлен в сеть управления, но более конкретные маршруты к офису и виртуальному WAN направляют учебный трафик через `BR-GW`. См. [BR-CLIENT-netplan.yaml](configs/BR-CLIENT-netplan.yaml).

### 3.4. TCP, UDP, ICMP и номера протоколов

IP доставляет пакеты между адресами. Внутри него могут передаваться разные протоколы:

| Протокол | Назначение в лабе | Номер протокола в IPv4 |
|---|---|---|
| TCP | HTTP, SSH, соединения Xray | 6 |
| UDP | Служебный обмен IKE | 17 |
| ICMP | Проверки `ping`, сообщения об ошибках | 1 |
| GRE | Упаковка межофисных пакетов | 47 |
| ESP | Защищённые данные IPsec | 50 |
| OSPF | Обмен маршрутами | 89 |

У TCP и UDP дополнительно есть **порты**, которые помогают выбрать приложение внутри узла. Например, сервер слушает TCP-порт `8080`, SSH обычно работает на TCP-порту `22`.

**GRE 47 — не порт 47. ESP 50 — не порт 50.** Это значения другого поля: номера протокола в IP-заголовке.

### 3.5. HTTP, TLS и HTTPS

HTTP — протокол запросов и ответов веб-сервера. В нашей лабе HTTP-сервис возвращает строку:

```text
BKS3: protected HQ service
```

TLS — механизм защищённого соединения между приложениями: шифрование, целостность, проверка стороны по сертификату. HTTPS — HTTP поверх TLS.

У нас конечный сервис на `10.1.50.10:8080` работает по обычному HTTP. Его защита зависит от выбранного пути: либо IPsec между шлюзами, либо TLS между узлами Xray. Последний участок `HQ-GW → HQ-SRV` проходит по серверной LAN без TLS. Называть сам тестовый сервер HTTPS-сервером нельзя.

## 4. Карта адресов и два пути к серверу

| Узел | WAN | LAN | GRE | Управление |
|---|---|---|---|---|
| HQ-GW | `203.0.113.10` | `10.1.50.1/26` | `172.16.0.1/30` | `192.168.15.211` |
| BR-GW | `203.0.113.20` | `10.2.20.1/24` | `172.16.0.2/30` | `192.168.15.212` |
| HQ-SRV | — | `10.1.50.10/26` | — | `192.168.15.213` |
| BR-CLIENT | — | `10.2.20.42/24` | — | `192.168.15.214` |
| XRAY-RELAY | `203.0.113.30` | — | — | `192.168.15.215` |

На обоих шлюзах `ens3` — WAN, `ens4` — LAN, `ens5` — управление. У клиента, сервера и relay имена интерфейсов нужно смотреть в их собственных netplan-файлах: одинаковая роль не гарантирует одинаковое имя.

**Путь А: обычный запрос через Site-to-Site VPN.**

```text
BR-CLIENT          BR-GW                         HQ-GW          HQ-SRV
10.2.20.42 → 10.2.20.1 → [GRE внутри IPsec] → 10.1.50.1 → 10.1.50.10:8080
                          внешний WAN
```

**Путь Б: запрос приложения через каскад Xray.**

```text
curl → локальный Xray → BR-GW с SNAT → XRAY-RELAY → Xray на HQ-GW → HQ-SRV
       127.0.0.1:1080                  TLS #1        TLS #2         HTTP
```

Здесь первый TLS-участок начинается на клиенте и заканчивается на relay. `BR-GW` только пересылает его пакеты и меняет исходный адрес. Второй начинается на relay и заканчивается на HQ-GW.

**Каскад Xray не вложен в GRE/IPsec. Это отдельный способ попасть к тому же сервису через виртуальный WAN.**

## 5. GRE: виртуальный канал между шлюзами

GRE расшифровывается как Generic Routing Encapsulation. Главная идея — вложить исходный пакет в другой пакет, чтобы доставить его между концами туннеля.

Упрощённо до защиты IPsec:

```text
Внешний IP: 203.0.113.20 → 203.0.113.10
└── GRE
    └── Внутренний IP: 10.2.20.42 → 10.1.50.10
        └── TCP → HTTP-запрос
```

Внешняя сеть доставляет пакет по WAN-адресам шлюзов. Внутренние адреса клиента и сервера сохраняются внутри.

На шлюзах появляется интерфейс `tun0`. Это программный сетевой интерфейс, с которым Linux может работать примерно как с обычным сетевым подключением: назначать адрес, отправлять пакеты, запускать поверх него OSPF.

На HQ-GW используются команды из [HQ-GW-gre.service](configs/HQ-GW-gre.service):

```sh
ip tunnel add tun0 mode gre local 203.0.113.10 remote 203.0.113.20 ttl 64
ip address add 172.16.0.1/30 dev tun0
ip link set tun0 mtu 1400 up
```

Первая создаёт туннель между WAN-адресами. Вторая даёт его локальному концу внутренний адрес. Третья включает интерфейс и ограничивает размер пакета. На BR-GW адреса концов зеркальные, а адрес `tun0` — `172.16.0.2/30`.

Сеть `/30` здесь содержит два обычных адреса узлов — `.1` и `.2`, что удобно для связи двух шлюзов.

GRE нужен в нашей реализации ещё и для переноса multicast-пакетов OSPF. Multicast — передача группе получателей; OSPF использует её для части служебного обмена. GRE позволяет представить внешнюю сеть как удобное соединение между двумя маршрутизаторами.

Сам GRE не проверяет личность соседнего шлюза и не шифрует содержимое. Для защиты мы добавили IPsec.

## 6. IPsec: кто договаривается о ключах и кто шифрует данные

### 6.1. IPsec, strongSwan и ядро Linux — разные вещи

**IPsec** — набор сетевых механизмов защиты IP-трафика.

**strongSwan** — программа, которая организует переговоры, аутентификацию и управление ключами. В наших протоколах виден её процесс `charon`.

**Ядро Linux** непосредственно обрабатывает защищаемые пакеты: применяет установленные политики и состояния IPsec. Для этого используется подсистема XFRM.

То есть strongSwan договаривается, а ядро выполняет защиту пакетов по результатам договорённости. Не нужно представлять, что каждый пользовательский пакет обязательно проходит через процесс strongSwan как через прокси.

### 6.2. IKEv2: договориться перед передачей

IKE — Internet Key Exchange, обмен ключами. `v2` означает вторую версию протокола.

Шлюзам нужно согласовать алгоритмы, получить общий ключевой материал и убедиться, что они разговаривают с разрешённым соседом. Упрощённая последовательность:

1. Шлюзы обмениваются параметрами и выполняют обмен Диффи — Хеллмана.
2. Проверяют друг друга с помощью общего секрета PSK.
3. Создают согласованные параметры защиты данных.
4. Затем обновляют ключи и следят за доступностью соседа.

Это учебное описание логики, а не полный разбор всех сообщений IKEv2.

### 6.3. PSK: общий секрет для аутентификации

PSK — Pre-Shared Key, заранее распределённый секрет. Он заранее установлен на обоих шлюзах и используется для подтверждения их подлинности.

Это не означает «весь трафик напрямую шифруется содержимым файла с паролем». Ключи сеанса вырабатываются в ходе IKE, а PSK участвует в аутентификации.

Секрет находится в `/etc/ipsec.secrets`, а не в основном конфиге. В репозитории и гайде его значение отсутствует.

Права `600` означают:

- владелец файла может читать и записывать;
- группа не имеет доступа;
- остальные пользователи не имеют доступа.

При владельце `root` это ограничивает обычный доступ к секрету root-пользователем. Разделение конфигурации и секрета помогает хранить несекретную часть в Git. Для большой инфраструктуры общие PSK усложняют индивидуальный отзыв доступа; часто рассматривают сертификаты и централизованный жизненный цикл ключей.

### 6.4. Что означает строка IKE

В [HQ-GW-ipsec.conf](configs/HQ-GW-ipsec.conf) записано:

```ini
ike=aes256-sha256-modp2048!
```

Это набор параметров для защиты **служебного обмена IKE**:

- `aes256` — AES с ключом 256 бит; в этом предложении согласован режим CBC;
- `sha256` — используется для механизмов целостности и выработки ключевого материала IKE; в выводе видны HMAC и PRF на SHA-256;
- `modp2048` — группа Диффи — Хеллмана с 2048-битным модулем;
- `!` — в используемом формате `ipsec.conf` ограничивает предложение указанным набором, без добавления стандартных наборов strongSwan.

**Шифрование** скрывает содержимое. **Контроль целостности** обнаруживает изменение. **Аутентификация** проверяет, с кем установлена связь. Это связанные, но разные задачи.

SHA-256 сам по себе не шифрует. HMAC — способ проверки подлинности сообщения с использованием секретного ключа и хеш-функции. PRF — функция, используемая при получении ключевого материала.

Диффи — Хеллман помогает получить общий секрет через наблюдаемый канал, но сам по себе не подтверждает личность собеседника. Поэтому аутентификация нужна отдельно.

Разбор синтаксиса алгоритмов: [официальная документация strongSwan](https://docs.strongswan.org/docs/latest/config/proposals.html).

### 6.5. ESP: защищать пользовательские пакеты

ESP — Encapsulating Security Payload, механизм IPsec для защиты данных. У нас:

```ini
esp=aes256gcm16-modp2048!
```

- AES использует ключ 256 бит.
- GCM одновременно обеспечивает шифрование и проверку целостности/подлинности защищаемых данных.
- `16` задаёт 16-байтовую длину проверочного тега, а не длину ключа AES.
- `modp2048` задаёт группу дополнительного обмена ключами при обновлении CHILD SA; это относится к свойству PFS — независимости новых ключей от одного лишь прежнего ключевого материала. Наличие параметра в конфиге и доказательство всех сценариев обновления — разные вещи.

Здесь не нужен отдельный SHA-256 для целостности ESP: эту задачу выполняет GCM. AES-CBC/SHA-256 в IKE и AES-GCM в ESP не противоречат друг другу — они относятся к разному трафику.

### 6.6. Транспортный режим: что именно защищено

Наши строки:

```ini
type=transport
leftprotoport=47
rightprotoport=47
```

Мы защищаем GRE-пакеты между WAN-адресами шлюзов. Упрощённый вид на внешнем канале:

```text
Видимый внешний IP: 203.0.113.20 → 203.0.113.10
└── ESP
    └── зашифровано: GRE + исходный IP-пакет + данные
```

Внешние адреса нужны оператору для доставки и остаются видимыми. Внутренние адреса и HTTP-содержимое находятся внутри защищённой части.

Транспортный режим защищает содержимое внешнего IP-пакета. В туннельном режиме IPsec дополнительно упаковывает защищаемый IP-пакет целиком под новый внешний IP-заголовок. У нас нужная упаковка уже сделана GRE, поэтому выбран транспортный режим IPsec.

Селектор `47` означает: защищать именно GRE. Он не означает «защитить вообще всё между этими машинами». Например, Xray TLS на TCP/443 не попадает под этот GRE-селектор.

### 6.7. SA, SPI, ESTABLISHED и INSTALLED

SA — Security Association, согласованный контекст защиты: алгоритмы, ключи, время жизни и другие параметры.

- IKE SA защищает служебный обмен IKE.
- CHILD SA организует защиту данных ESP; для двух направлений устанавливаются соответствующие состояния.
- SPI — идентификатор, по которому получатель выбирает нужное состояние защиты для входящего ESP-пакета. Это не пароль.

В `ipsec statusall` у нас сохранены:

```text
ESTABLISHED
INSTALLED, TRANSPORT
AES_GCM_16_256
```

Первая строка подтверждает установленную IKE SA, вторая — установленные параметры защиты данных, третья — согласованный алгоритм ESP. Счётчики пакетов дополняют картину, но даже эти строки сами по себе ещё не заменяют проверку трафика и приложения.

### 6.8. Время жизни и обнаружение отказов

| Параметр | Смысл в нашем конфиге |
|---|---|
| `ikelifetime=3h` | Время жизни IKE SA |
| `lifetime=1h` | Время жизни защиты данных CHILD SA |
| `dpddelay=10s` | Интервал, связанный с проверкой живости соседа при отсутствии подтверждающего трафика |
| `dpdaction=restart` | Попытаться восстановить соединение при обнаружении недоступности |
| `keyingtries=%forever` | Не ограничивать число попыток установки |
| `auto=start` | Инициировать соединение при запуске |

Это не обещание, что любой отказ обнаружится строго за десять секунд: реальное время зависит от обмена, повторных передач и реализации IKEv2.

UDP/500 используется для IKE; UDP/4500 разрешён для связанных с NAT traversal сценариев. NAT traversal позволяет IPsec работать через устройства, меняющие адреса. В сохранённом WAN-захвате нашей лабы наблюдался обычный ESP, поэтому утверждать, что данные у нас фактически шли в UDP/4500, нельзя.

## 7. OSPF и FRRouting: откуда берутся маршруты

### 7.1. Почему туннеля недостаточно

Создать GRE и защитить его — ещё не значит сообщить шлюзам обо всех удалённых LAN.

BR-GW должен узнать, что сеть `10.1.50.0/26` доступна через HQ-GW. HQ-GW должен знать обратный путь в `10.2.20.0/24`. Без обратного маршрута запрос может дойти, а ответ — потеряться.

Можно прописать маршруты вручную. Мы использовали динамический обмен через OSPF — Open Shortest Path First.

### 7.2. Что делает OSPF

OSPF находит соседние маршрутизаторы, обменивается с ними сведениями о связях и вычисляет пути. В нашей простой сети он позволяет каждому шлюзу узнать LAN другого.

FRRouting, сокращённо FRR, — пакет программ маршрутизации. В нём `ospfd` реализует OSPF, а `zebra` взаимодействует с системной таблицей маршрутов. `vtysh` — интерфейс команд для просмотра и настройки FRR.

Пакеты после установки маршрута пересылает ядро Linux. OSPF не сопровождает каждый HTTP-запрос отдельной командой.

### 7.3. Чтение нашего конфига

Фрагмент [BR-GW-frr.conf](configs/BR-GW-frr.conf):

```text
interface tun0
 ip ospf network point-to-point
 ip ospf hello-interval 2
 ip ospf dead-interval 8
router ospf
 ospf router-id 10.2.254.254
 passive-interface default
 no passive-interface tun0
 network 172.16.0.0/30 area 0.0.0.0
 network 10.2.20.0/24 area 0.0.0.0
```

- `point-to-point`: на канале два маршрутизатора; выбор главного маршрутизатора сегмента не нужен.
- `hello-interval 2`: приветственные сообщения каждые две секунды.
- `dead-interval 8`: при отсутствии приветствий примерно восемь секунд сосед признаётся недоступным.
- `router-id`: идентификатор маршрутизатора. Он похож на IP-адрес, но не обязан быть адресом интерфейса или шлюзом для пакетов.
- `passive-interface default`: по умолчанию не устанавливать OSPF-соседство на интерфейсах.
- `no passive-interface tun0`: разрешить активный обмен только в туннеле.
- `network ... area ...`: выбрать интерфейсы соответствующих сетей для участия в OSPF и назначить область.

`area 0` — основная область OSPF. Для двух шлюзов одной области достаточно.

LAN пассивная: её сеть объявляется соседу, но клиентские компьютеры не приглашаются стать OSPF-маршрутизаторами. WAN и сеть управления не включены в OSPF.

Смысл passive-interface и типы сетей описаны в [документации FRR](https://docs.frrouting.org/en/latest/ospfd.html).

### 7.4. Как читать результат

```text
10.1.50.0/26 via 172.16.0.1 dev tun0 proto ospf metric 20
```

Это означает: сеть сервера доступна через туннельного соседа `172.16.0.1`, интерфейс `tun0`; маршрут получен от OSPF. `metric` — стоимость пути, не задержка в миллисекундах.

Состояние соседа `Full` означает, что соседство сформировано и базы сведений OSPF синхронизированы. Оно не доказывает, что firewall разрешает HTTP.

У нас нет резервного межофисного пути на практическом стенде. Поэтому при потере туннеля OSPF удаляет маршрут, но не может выбрать несуществующий запасной канал.

## 8. Полный путь обычного HTTP-запроса

Разберём команду с BR-CLIENT:

```sh
curl --interface 10.2.20.42 http://10.1.50.10:8080
```

1. `curl` создаёт TCP-соединение к серверу, используя адрес клиента `10.2.20.42`.
2. Таблица маршрутов клиента направляет пакет к `10.2.20.1`, то есть BR-GW.
3. BR-GW смотрит маршрут, полученный через OSPF: до сервера идти через `tun0`.
4. Firewall проверяет, что клиенту разрешён TCP/8080 к этому серверу.
5. GRE упаковывает исходный пакет в пакет между WAN-адресами шлюзов.
6. Политика IPsec требует защиты GRE. Ядро применяет ESP.
7. По виртуальному WAN передаётся ESP между `203.0.113.20` и `203.0.113.10`.
8. HQ-GW проверяет защищённый пакет, расшифровывает его и обрабатывает GRE.
9. Из туннеля извлекается исходный пакет к `10.1.50.10:8080`.
10. HQ-GW проверяет транзит firewall и передаёт пакет в серверную LAN.
11. HTTP-сервер обрабатывает запрос. Ответ возвращается через шлюз офиса и тот же защищённый межофисный путь.

Межофисный NAT здесь не применяется: сервер видит исходный адрес филиала `10.2.20.42`. Шифрование действует между шлюзами; участки клиент → BR-GW и HQ-GW → сервер не получают шифрование IPsec от этой схемы.

## 9. Firewall: разрешить ровно нужное

### 9.1. iptables и цепочки

iptables — средство настройки правил обработки пакетов Linux. Наши правила сохранены в `*-rules.v4`.

| Цепочка | Какие пакеты рассматривает | Пример |
|---|---|---|
| INPUT | Адресованные самой машине | IKE к шлюзу, SSH к шлюзу |
| FORWARD | Пересылаемые через машину | Запрос клиента к серверу через шлюз |
| OUTPUT | Созданные самой машиной | Исходящий GRE или соединение локального Xray |

Это существенное различие: открыть INPUT/8080 на маршрутизаторе недостаточно для транзита к серверу за ним.

У нас INPUT и FORWARD по умолчанию `DROP`: пакет блокируется, если не найдено разрешение. OUTPUT по умолчанию `ACCEPT`: исходящие подключения не ограничены столь же строго. Поэтому утверждение «на шлюзах весь трафик во всех направлениях запрещён по умолчанию» было бы неверным.

### 9.2. Чтение правила

На HQ-GW:

```text
-A FORWARD -i tun0 -o ens4 -s 10.2.20.0/24 -d 10.1.50.10/32 -p tcp --dport 8080 -j ACCEPT
```

Читается так: добавить в FORWARD правило, которое разрешает TCP-пакет из сети филиала к конкретному серверу на порт 8080, если он пришёл из туннеля и выходит в LAN.

- `-i` и `-o` — входной и выходной интерфейсы;
- `-s` и `-d` — адреса источника и назначения;
- `-p` — протокол;
- `--dport` — порт назначения;
- `-j ACCEPT` — пропустить подходящий пакет.

На BR-GW правильное направление исходного запроса — `ens4 → tun0`, а на HQ-GW — `tun0 → ens4`.

В сохранённых конфигурациях есть также зеркальные записи с теми же адресами источника/назначения, но неподходящим для обычного запроса направлением интерфейсов. Это избыточные правила, их не стоит заучивать как обязательную часть схемы. Ответы разрешает отслеживание состояния соединений.

### 9.3. conntrack: узнавать ответный трафик

```text
-m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
```

conntrack хранит состояние сетевых потоков. `ESTABLISHED` позволяет пропустить пакеты уже отслеживаемого обмена, в том числе ответы. `RELATED` — связанные потоки и некоторые сообщения об ошибках.

Это не означает «любой ACK-пакет считается доверенным»: используются сведения о состоянии потока в ядре.

### 9.4. Fail closed: при отказе защиты блокировать

Нашему GRE нельзя незаметно продолжить работу открытым текстом после падения IPsec.

На входе WAN открытый GRE отбрасывается **до** общего разрешения ESTABLISHED. Входной GRE разрешается при наличии признака входной IPsec policy.

На выходе разрешается GRE, которому соответствует исходящая IPsec policy, а оставшийся GRE блокируется:

```text
-A OUTPUT -o ens3 -p gre -m policy --dir out --pol ipsec -j ACCEPT
-A OUTPUT -o ens3 -p gre -j DROP
```

`policy` проверяет связь пакета с политикой IPsec, а не просто факт запуска службы strongSwan. Порядок правил важен: более раннее подходящее разрешение может сделать поздний запрет бесполезным.

Такую логику называют **fail closed**: при проблеме с защитой доступ пропадает. Мы подтвердили это отдельной проверкой отказа и захватом WAN.

### 9.5. SNAT только для Xray

NAT — преобразование сетевых адресов. SNAT меняет адрес источника.

Для первого перехода Xray на BR-GW есть узкое правило:

```text
-s 10.2.20.42/32 -d 203.0.113.30/32 -o ens3 -p tcp --dport 443
-j SNAT --to-source 203.0.113.20
```

Оно применяется только к TCP/443 клиента на relay. Relay видит подключение от WAN-адреса BR-GW `203.0.113.20`. Так обратный трафик идёт к BR-GW, где conntrack выполняет обратное преобразование. Relay не нужен маршрут в клиентскую LAN.

Это не скрывает личность пользователя в смысле анонимности и не шифрует данные. Это изменение адреса для данного пути. Обычный HTTP через GRE/IPsec под это правило не подходит.

## 10. MTU и MSS: почему большие пакеты могут ломаться

MTU — Maximum Transmission Unit: максимальный размер IP-пакета, который можно передать через интерфейс без фрагментации на этом уровне.

GRE и IPsec добавляют заголовки и служебные данные. Если взять внутренний пакет размером с допустимый внешний пакет, после упаковки он может оказаться слишком большим.

У нас MTU интерфейса `tun0` установлен в 1400 байт. Это выбранное для стенда значение с запасом под упаковку, а не универсальный размер для любого VPN.

Проверка:

```sh
ping -M do -s 1372 -I 10.2.20.42 -c 3 10.1.50.10
```

- `-M do` запрещает фрагментацию проверяемого IPv4-пакета;
- `-s 1372` задаёт данные ICMP;
- ещё 8 байт занимает заголовок ICMP, 20 байт — обычный IPv4-заголовок;
- всего получается внутренний IP-пакет 1400 байт;
- `-I` фиксирует исходный адрес, `-c 3` задаёт число запросов.

В сохранённом результате прошли все три пакета. Это показывает проходимость выбранного размера в проверенных условиях, но не доказывает, что 1400 — максимально возможное значение.

MSS — Maximum Segment Size, размер TCP-данных в сегменте. Firewall использует `TCPMSS --clamp-mss-to-pmtu`, чтобы подстроить объявляемый MSS в TCP SYN-пакетах под доступный MTU пути. Это уменьшает риск ситуации «маленький ping работает, а передача сайта зависает из-за крупных пакетов». Правило относится к TCP и не исправляет автоматически все проблемы размера для UDP и других протоколов.

## 11. Xray: доступ к приложению через цепочку посредников

### 11.1. Зачем он в этой лабе

GRE/IPsec показывает связь сетей через шлюзы. Xray показывает другой подход: приложение явно обращается к локальному прокси, а тот отправляет соединение через заданную цепочку.

Мы разрешаем через эту цепочку только TCP к `10.1.50.10:8080`. Это полезный пример ограничения прикладного доступа. В нём нет автоматического резервирования: отказ любого обязательного звена ломает цепочку.

### 11.2. SOCKS5: как curl передаёт запрос прокси

На BR-CLIENT Xray слушает `127.0.0.1:1080` по SOCKS5. Приложение сообщает прокси, куда установить соединение.

```sh
curl --socks5-hostname 127.0.0.1:1080 http://10.1.50.10:8080
```

`127.0.0.1` — loopback: обращение к своей машине. Вход SOCKS не опубликован на WAN или всей LAN. `auth: noauth` означает отсутствие аутентификации на этом локальном входе; доступные локальные процессы всё равно могут к нему обращаться. `udp: false` отключает UDP на этом входе.

Опция `--socks5-hostname` поручает разрешение имён прокси, если цель задана именем. В нашей команде цель — числовой IP, поэтому разрешать имя цели не требуется.

### 11.3. inbound, routing, outbound

Каждый Xray-конфиг состоит из трёх основных частей:

```text
inbound → правила routing → outbound
куда принимаем             куда отправляем дальше
```

- `inbounds` — входы: адрес, порт, протокол и параметры приёма.
- `routing` — выбор действия по адресу, порту и другим признакам запроса.
- `outbounds` — выходы: следующий прокси, прямое соединение или блокировка.
- `tag` — внутреннее имя входа или выхода. Наши `entry`, `next`, `blocked` — метки, а не специальные сетевые протоколы.

На каждом узле сначала разрешён нужный адрес/порт, затем остальные запросы данного входа отправляются в `blackhole`, то есть блокируются.

Конфиги: [клиент](configs/BR-CLIENT-xray.json), [relay](configs/XRAY-RELAY-xray.json), [шлюз офиса](configs/HQ-GW-xray.json).

### 11.4. VLESS, UUID и TLS

VLESS — протокол прокси-обмена, который мы используем между узлами Xray. UUID — идентификатор клиентского доступа в конфигурации. Для двух переходов заданы разные UUID.

В наших конфигах VLESS стоит `encryption: none` или `decryption: none`. Это не означает, что сетевой канал открыт: защиту обеспечивает отдельно настроенный TLS. Рассматривать UUID как шифрование нельзя.

На первом переходе клиент устанавливает TLS к relay, на втором relay устанавливает новый TLS к HQ-GW. Минимальная версия TLS задана `1.3`.

Порт `443` привычен для HTTPS, но сам по себе номер порта ничего не говорит о протоколе внутри. У нас на нём VLESS поверх TLS, а не обычный веб-сайт. Настройка не доказывает нераспознаваемость или анонимность трафика.

### 11.5. CA, сертификат, приватный ключ и serverName

CA — Certificate Authority, центр сертификации. В лабе создан собственный учебный CA, которому доверяют узлы каскада.

- `ca.crt` — публичный сертификат доверенного CA.
- `server.crt` — сертификат конкретного сервера.
- `server.key` — его закрытый ключ, который должен оставаться секретным.
- `serverName` — ожидаемое имя сервера при TLS-проверке.

Клиент подключается к IP `203.0.113.30`, но проверяет имя `relay.bks3.test`. Relay подключается к IP `203.0.113.10`, проверяя `hq.bks3.test`. Это допустимо: IP определяет, куда установить соединение, а ожидаемое имя — чью подлинность проверять по сертификату.

Проверка должна подтвердить доверенную цепочку и соответствие имени. В нашей реализации она не отключена. Если принимать любой сертификат, шифрование может установиться с подменённым сервером.

Это **не mTLS**: конфиги не показывают взаимную TLS-аутентификацию клиентскими сертификатами. Клиент проверяет серверный сертификат, а разрешение клиента в VLESS связано с UUID. mTLS упомянут в архитектурном проекте как возможное решение для подрядчика.

### 11.6. Что делает каждый узел

| Узел Xray | Принимает | Отправляет |
|---|---|---|
| BR-CLIENT | SOCKS5 на loopback | VLESS/TLS к relay |
| XRAY-RELAY | VLESS/TLS от клиента через BR-GW | Новый VLESS/TLS к HQ-GW |
| HQ-GW | VLESS/TLS от relay | Прямое TCP-соединение к серверу |

Последний выход называется `freedom`. В нашем конфиге это прямое соединение с дополнительными `finalRules`: разрешён конкретный адрес/порт, затем стоит блокировка остальных целей.

Разделение прокси-протокола и защиты транспорта описано в [документации Xray](https://xtls.github.io/en/config/transport.html).

Это защита в несколько слоёв: ограничение в routing и ограничение конечного выхода. Конкретный синтаксис относится к версии Xray, использованной в стенде, а не к любой исторической версии программы.

### 11.7. Границы защиты каскада

Каскад не создаёт одно непрерывное TLS-соединение от curl до веб-сервера. На relay первая TLS-сессия заканчивается и начинается вторая. Relay является доверенным посредником и обрабатывает содержимое прокси-потока.

На HQ-GW вторая TLS-сессия заканчивается, и к серверу идёт обычный HTTP. Для сквозной защиты до приложения можно было бы добавить HTTPS на самом сервисе, но в нашей реализации его нет.

Сервер видит TCP-подключение, созданное HQ-GW, а не исходное сетевое соединение клиента. Это ещё одно отличие от маршрутизируемого пути без межофисного NAT.

## 12. Linux-настройки, которые обеспечивают работу схемы

### 12.1. netplan: постоянная адресация

Netplan описывает сетевые интерфейсы и маршруты в YAML. YAML — текстовый формат со значимыми отступами.

Файлы `*-netplan.yaml` содержат адреса LAN, WAN, управления и статические маршруты конечных узлов. OSPF-конфиг хранится отдельно: не все маршруты задаются в netplan.

Здесь полезно различать постоянную конфигурацию и текущее состояние. Команда `ip route ...` может изменить состояние прямо сейчас, а файл netplan нужен, чтобы настройка воспроизвелась после загрузки.

### 12.2. sysctl: параметры ядра

На шлюзах:

```ini
net.ipv4.ip_forward=1
net.ipv4.conf.all.rp_filter=0
net.ipv4.conf.default.rp_filter=0
```

`ip_forward=1` разрешает ядру пересылать IPv4-пакеты между интерфейсами. Без этого Linux не выполнит роль маршрутизатора, даже если адреса и маршруты правильные.

`rp_filter` связан с проверкой обратного пути к адресу источника. В сложных схемах с туннелями и несколькими интерфейсами строгая проверка может отбрасывать допустимые пакеты. В стенде она отключена, для `tun0` это также явно сделано службой GRE.

Отключение проверки — ослабление одного из механизмов фильтрации, а не универсальная «безопасная настройка VPN». В рабочей сети нужно выбирать режим под реальную маршрутизацию и отдельно ограничивать допустимые источники. Наши firewall-правила дают часть таких ограничений.

### 12.3. systemd: конфигурация должна пережить reboot

systemd — менеджер служб Linux. Unit-файл описывает, что запускать, от чьего имени, после каких этапов загрузки и с какими ограничениями.

Основные службы у нас:

| Служба | Роль |
|---|---|
| `bks3-gre` | Создать и настроить `tun0` |
| `strongswan-starter` | Запустить подсистему управления IPsec |
| `frr` | Запустить программы динамической маршрутизации |
| `netfilter-persistent` | Восстановить сохранённые правила firewall |
| `xray` | Запустить прокси |
| `bks3-web` | Запустить тестовый HTTP-сервис |

`systemctl enable` включает запуск при загрузке. `systemctl start` запускает сейчас. `enable --now` делает оба действия. `daemon-reload` сообщает systemd, что unit-файлы изменились.

GRE-служба имеет `Type=oneshot`: команды настройки выполняются и завершаются. `RemainAfterExit=yes` сохраняет активное состояние unit после их успешного выполнения. Сам GRE затем работает в ядре, отдельный непрерывно работающий GRE-процесс не нужен. Поэтому `active (exited)` для такой службы может быть нормой; это ещё не доказательство передачи данных.

`After=network-online.target` задаёт порядок запуска, а `Wants=network-online.target` подключает соответствующую зависимость. Это не гарантирует доступность удалённого узла: порядок загрузки и работоспособность сети — разные вещи.

Семантика oneshot описана в [systemd.service](https://freedesktop.org/software/systemd/man/latest/systemd.service.html).

### 12.4. Ограничение прав служб

В [xray.service](configs/xray.service) процесс работает от отдельного пользователя `xray`, а не постоянно от root.

- `CAP_NET_BIND_SERVICE` позволяет открыть привилегированный порт 443 без выдачи всех root-прав.
- `NoNewPrivileges=true` запрещает получение новых привилегий определёнными механизмами при запуске дочерних программ.
- `ProtectSystem=strict` делает файловую систему преимущественно доступной только для чтения внутри окружения службы.
- `ReadWritePaths=/var/log/xray` разрешает запись в каталог журналов.
- `ProtectHome=true` ограничивает доступ к домашним каталогам.
- `PrivateTmp=true` выделяет отдельное представление временных каталогов.
- `Restart=on-failure` перезапускает процесс при аварийном завершении; это не проверка того, отвечает ли удалённый сайт.

Веб-сервис использует `DynamicUser=yes`: systemd выделяет служебную учётную запись на время работы. Он запускает Python HTTP-сервер в `/srv/bks3` и привязывает его к LAN-адресу `10.1.50.10`, а не ко всем интерфейсам.

Параметры окружения и ограничений служб описаны в [systemd.exec](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html).

Эти ограничения уменьшают последствия компрометации, но не являются доказательством полной изоляции. Python `http.server` здесь — учебный источник ответа, не полноценный промышленный веб-сервер.

## 13. Архитектурные технологии из первой части работы

### 13.1. Site-to-Site и Client-to-Site

Site-to-Site связывает сети площадок через их шлюзы. Наша практика GRE/IPsec относится к этому типу, хотя firewall разрешает лишь ограниченный набор обращений.

Client-to-Site подключает отдельное устройство пользователя. В предыдущей БКС2 для такого доступа использовался WireGuard. Он не является частью нового GRE/IPsec-тракта БКС3.

### 13.2. SD-WAN

SD-WAN — Software-Defined Wide Area Network: подход и класс решений для программного централизованного управления связью площадок.

Для наших двадцати ПВЗ это означает возможность из одного места задавать шаблоны и политики, организовывать защищённые соединения, учитывать состояние оптики/LTE и выбирать транспорт для приложений.

Это не отдельный кабель и не другое название OSPF. Интернет предоставляет оператор; SD-WAN организует работу поверх доступных каналов.

**CPE** — Customer Premises Equipment, устройство на площадке клиента. **ZTP** — Zero-Touch Provisioning: первоначальное подключение устройства к системе управления с минимальной ручной настройкой на месте.

**CGNAT** — общий NAT оператора, при котором у площадки может не быть собственного доступного извне IPv4-адреса. Поэтому в проекте важны исходящие подключения от ПВЗ и поддержка прохождения NAT.

**Control Plane** отвечает за управляющие решения и распространение состояния; **Data Plane** пересылает пользовательские пакеты. В нашей практике OSPF относится к управлению маршрутами, а пересылка ядром по установленным маршрутам — к передаче данных. В проекте SD-WAN контроллеры и устройства также разделяют эти роли.

Выбор канала по потерям и задержке, централизованная регистрация и политики приложений — возможности выбранного SD-WAN-решения. Они не появляются автоматически от установки FRRouting.

### 13.3. Радиомост и зона Френеля

Радиомост передаёт данные между направленными антеннами. Для лаборатории в соседнем здании это позволяет обойтись без прокладки кабеля между зданиями.

Недостаточно просто видеть второе здание. Вокруг прямой линии между антеннами есть пространственная зона Френеля: препятствия в ней могут ухудшать связь. Нужны обследование трассы, оценка помех, частот, мощности и полезной пропускной способности.

Мы не вычисляли скорость и дальность без исходных данных и не монтировали оборудование. В проекте конфиденциальные данные поверх радиоканала должны защищаться IPsec; резервный канал уменьшает зависимость от радиолинии.

### 13.4. DMZ и обратный прокси

DMZ — отдельный сетевой сегмент для сервисов, доступных с менее доверенной стороны. Он ограничивает прямой доступ извне к внутренним системам.

Обратный прокси принимает обращения к сервису от имени компании и передаёт их внутреннему серверу. Для подрядчика проект предусматривает защищённый прикладной вход и разрешение только нужного сервиса.

Это архитектурная идея. Не следует называть учебный каскад Xray полностью реализованным промышленным HTTPS reverse proxy с mTLS: у нас другая конкретная реализация ограниченного доступа.

### 13.5. QinQ и аппаратное ускорение

QinQ добавляет внешний VLAN-тег к внутреннему тегу клиента и позволяет оператору переносить клиентские VLAN через свою L2-сеть. Это полезно при наличии подходящей услуги оператора, но само по себе не шифрует данные. Для двадцати ПВЗ разных операторов мы выбрали другой подход.

Hardware Offloading — выполнение части обработки специализированным оборудованием вместо обычной программной обработки CPU. Например, это может касаться шифрования или пересылки. В лабе аппаратное ускорение не измерялось: утверждать прирост производительности по факту наличия AES нельзя.

### 13.6. Резервирование двух ЦОД

Два здания с серверами не обеспечивают готовое резервирование приложения. Нужны репликация данных, контроль состояния, независимые каналы/питание и механизм переключения клиентов.

В проекте офису соответствует `10.1.0.0/16`, второму ЦОД зарезервирован `10.3.0.0/16`, филиалам выделяются непересекающиеся подсети из `10.2.0.0/16`. Все двадцать ПВЗ не должны становиться одной растянутой LAN.

На практическом стенде резервного ЦОД и автоматического переключения сервисов нет. Каскад прокси тоже не резерв: его звенья последовательны, а не взаимозаменяемы.

## 14. Какие инженерные практики мы применили

| Практика | Где видно у нас | Зачем |
|---|---|---|
| Разделение ролей сетей | LAN, WAN, управление | Понимать и контролировать путь трафика |
| Минимально необходимый доступ | Конкретный сервер, ICMP и TCP/8080 | Не открывать всю сеть из-за одного сервиса |
| Блокировка по умолчанию | INPUT/FORWARD DROP | Неизвестный входной/транзитный трафик не разрешается автоматически |
| Fail closed | Блокировка GRE без IPsec | Не передавать данные открыто при отказе защиты |
| Несколько уровней ограничений | Firewall, Xray routing, finalRules | Не полагаться на одну точку принятия решения |
| Проверка стороны соединения | PSK в IKE, сертификаты в TLS | Не путать шифрование с проверкой собеседника |
| Отделение секретов | PSK и закрытые ключи вне публичных файлов | Не публиковать секреты вместе с конфигом |
| Минимизация прав процессов | Отдельные пользователи и systemd-ограничения | Снизить последствия ошибки или взлома службы |
| Воспроизводимая загрузка | netplan, systemd, persistent firewall | Не зависеть от вручную введённых временных команд |
| Положительные и отрицательные проверки | Разрешённый HTTP и запрещённый порт | Проверить и доступность, и ограничения |
| Проверка отказов | Остановка IPsec/relay и восстановление | Проверить поведение при потере компонента |
| Проверка после reboot | Протокол `after-reboot.txt` | Убедиться, что конфигурация переживает перезагрузку |
| Контроль фактического пути | Источник запроса, traceroute, WAN-захват | Не принять служебный обход за работающий VPN |

Это практики, показанные в учебном масштабе. Полного промышленного мониторинга, управления секретами, резервирования и аудита всех угроз в стенде нет.

## 15. Проверки: что каждая действительно доказывает

### 15.1. Маршрут клиента

На BR-CLIENT:

```sh
ip route get 10.1.50.10
```

Смотрим шлюз `10.2.20.1`, интерфейс LAN и исходный адрес `10.2.20.42`. Это показывает выбранный локальный маршрут, а не гарантированную доставку до сервера.

### 15.2. Ping и HTTP

```sh
ping -I 10.2.20.42 -c 4 10.1.50.10
curl --interface 10.2.20.42 http://10.1.50.10:8080
```

Ping проверяет ICMP-обмен. HTTP-запрос проверяет TCP-путь и ответ приложения. Успешный ping без curl не доказывает доступность сайта. Успешный curl сам по себе не доказывает шифрование на WAN.

### 15.3. Соседство и маршрут OSPF

На BR-GW:

```sh
sudo vtysh -c 'show ip ospf neighbor'
ip route show proto ospf
```

Ожидаем Full и маршрут к `10.1.50.0/26`. В сохранённом протоколе строка `vtysh -c show_ip_ospf_neighbor` — сокращённая запись, а не корректная команда для копирования. Выше приведён нормальный синтаксис.

### 15.4. IPsec и WAN

```sh
sudo ipsec statusall
```

Ищем установленную IKE SA, установленную CHILD SA, режим TRANSPORT и счётчики. Для проверки состояния ядра также полезны `sudo ip xfrm policy` и `sudo ip xfrm state`, но вывод последней команды может содержать ключевой материал: его нельзя публиковать или включать в скриншоты без очистки.

В лабе захват выполнялся на WAN-мосту хоста PNETLab, вне сетевого стека гостевого шлюза. Это уменьшает неоднозначность: внутри гостя захват может видеть пакеты до или после обработки IPsec.

В сохранённом [WAN-encryption.txt](outputs/WAN-encryption.txt) виден ESP между WAN-адресами. Вывод относится к конкретному месту, фильтру и времени захвата. Он не означает «во всей сети никогда не бывает другого трафика».

### 15.5. Xray

```sh
curl --socks5-hostname 127.0.0.1:1080 http://10.1.50.10:8080
curl --max-time 5 --socks5-hostname 127.0.0.1:1080 http://10.1.50.10:22
```

Первая команда должна получить тестовую строку. Вторая — завершиться неуспешно: порт запрещён политикой каскада. Форма ошибки может зависеть от версии и момента закрытия соединения; её код не заменяет анализ политики.

Журналы двух узлов показывают `entry → next` для одной цели. Они подтверждают обработку запроса обоими звеньями. Один успешный curl без этих журналов ещё не доказывает всю заданную цепочку.

### 15.6. Отказы и восстановление

Сохранённый протокол [failure-tests.txt](outputs/failure-tests.txt) фиксирует два эксперимента:

- при остановке IPsec пропал ping, затем исчез маршрут OSPF; открытый GRE на WAN не наблюдался;
- при остановке relay запрос через SOCKS не прошёл; после запуска relay снова получен ответ.

Остановка служб — вмешательство в работу стенда. Для самостоятельного обучения сначала изучай сохранённые результаты и команды чтения. Повторять остановку на общей сессии следует только в согласованное время, когда никто не использует соединение.

После reboot в [after-reboot.txt](outputs/after-reboot.txt) сохранены состояния служб, соседство, маршруты и ответы обоих HTTP-путей. Комбинация проверок сильнее одной надписи `active`.

## 16. Как разбираться, если что-то не работает

Проверяй по слоям. Не меняй сразу IPsec, OSPF и firewall: после нескольких изменений трудно установить причину.

### Ситуация А: вообще не открывается сервер

1. На клиенте проверь `ip route get 10.1.50.10`: выбран ли BR-GW.
2. На BR-GW посмотри `ip -br address` и `ip link show tun0`: есть ли нужные адреса и интерфейс.
3. Проверь `ipsec statusall`: установлена ли защита.
4. Проверь OSPF Full и маршрут к серверной сети.
5. Посмотри firewall и счётчики: `sudo iptables -nvL FORWARD --line-numbers`.
6. На сервере проверь `systemctl status bks3-web` и `ss -lnt`: слушает ли `10.1.50.10:8080`.
7. Проверь обратный маршрут сервера и HQ-GW.

Отсутствие пакетов в одном месте может быть следствием ошибки на предыдущем слое. Сам факт запущенной службы не исключает неправильную конфигурацию.

### Ситуация Б: IPsec установлен, а маршрута нет

Проверь GRE, адреса `tun0`, OSPF на обоих концах, совпадение hello/dead, область и разрешение OSPF на `tun0`. Просмотри `journalctl -u frr`. Не добавляй статический маршрут сразу: он может скрыть неисправный OSPF, который требуется показать в лабе.

### Ситуация В: ping проходит, а сайт нет

Проверь порт 8080, службу сервера, правила TCP, обратные ответы и MTU/MSS. ICMP и TCP обрабатываются разными правилами; работа одного не гарантирует работу другого.

### Ситуация Г: обычный curl работает, а через SOCKS нет

Тогда начни с Xray, а не с OSPF:

- слушает ли локальный `127.0.0.1:1080`;
- есть ли маршрут клиента к WAN через BR-GW;
- применяется ли нужный SNAT;
- доступен ли relay по TCP/443;
- совпадают ли UUID и параметры TLS каждого перехода;
- доверен ли CA и совпадает ли имя сертификата;
- что записано в `/var/log/xray/error.log` и `access.log`;
- разрешена ли цель в routing и finalRules.

Обычный путь и прокси-путь используют разные механизмы. Успех одного не означает исправность другого.

### Ситуация Д: работало до перезагрузки

Проверь постоянные файлы, `systemctl is-enabled`, журналы загрузки и `systemctl --failed`. Временные команды могли настроить только текущее состояние. Порядок запуска тоже может быть причиной: зависимостями systemd нужно управлять без циклов.

## 17. Ограничения и что улучшать в рабочей инфраструктуре

Это важная часть понимания, а не список «всё плохо»:

- Один WAN-сегмент не воспроизводит реальные потери, CGNAT и разнообразие маршрутов интернета.
- Один шлюз на площадку не даёт аппаратного резервирования.
- OSPF обнаруживает потерю пути, но без второго пути не сохраняет связь.
- PSK удобен для двух учебных шлюзов, но требует продуманного распределения и ротации при росте сети.
- Сеть управления отделена логически и ограничена правилами, но это не полностью изолированная физическая система управления.
- OUTPUT на шлюзах в целом разрешён; строгого белого списка всего исходящего трафика нет.
- `rp_filter` отключён ради выбранной схемы; эту настройку нельзя бездумно переносить в любой проект.
- Не все избыточные firewall-правила очищены: направление потока нужно понимать, а не копировать конфиг как идеальный образец.
- Xray защищает два отдельных участка TLS; доверенные посредники завершают эти соединения.
- Веб-сервис не имеет собственного TLS и является учебным.
- Успешные тесты от 27 октября подтверждают проверенные сценарии того запуска, а не бессрочную доступность стенда.

## 19. Как учиться по этому гайду

Не нужно начинать с заучивания `aes256gcm16-modp2048`. Сначала собери понятную картину.

### Проход 1: нарисовать сеть

Без конфигов нарисуй клиента, два шлюза, сервер и relay. Подпиши LAN, WAN и управление. Затем нарисуй двумя разными линиями обычный путь и прокси-путь.

Проверь себя: на первом пути участвуют GRE/IPsec, на втором — два TLS-соединения Xray. BR-GW на втором пути пересылает пакеты, но сам не становится первым TLS-сервером.

### Проход 2: проследить один пакет

Возьми запрос от `10.2.20.42` к `10.1.50.10:8080`. На каждом шаге отвечай:

1. Кто сейчас обрабатывает пакет?
2. Какие адреса видны внутри и снаружи?
3. Как выбран следующий узел?
4. Чем защищено содержимое на этом участке?
5. Какое правило разрешает проход?

Если можешь рассказать это без слов «оно просто идёт через VPN», основа уже понятна.

### Проход 3: читать конфиги парами

Сравни HQ-GW и BR-GW: GRE, IPsec, OSPF, firewall. Найди, что зеркально, а что различается из-за роли площадки. Не копируй один конфиг на другой шлюз без изменения адресов.

### Проход 4: сопоставлять утверждение и доказательство

К каждому утверждению подбери проверку:

- «Я знаю маршрут» → таблица маршрутов.
- «Соседство сформировалось» → OSPF Full.
- «Защита согласована» → IKE/CHILD SA.
- «На WAN передавался ESP» → внешний захват.
- «Приложение отвечает» → HTTP-ответ.
- «Лишний доступ закрыт» → отрицательная проверка.
- «Переживает reboot» → повторный обмен после загрузки.

Это универсальный навык: отличать желаемую конфигурацию от наблюдаемого поведения.

### Вопросы для самопроверки

Сначала ответь своими словами, затем сверься с короткими ответами ниже.

1. Почему одного GRE недостаточно для безопасной связи?
2. Что делает IKE, а что ESP?
3. Почему GRE 47 не означает TCP-порт 47?
4. Зачем OSPF, если GRE уже создан?
5. Что произойдёт при потере IPsec в нашей схеме?
6. Почему успешный ping не доказывает работу сайта?
7. Чем отличается обычный запрос от запроса через SOCKS?
8. Кто завершает TLS-соединения в каскаде?
9. Где используется SNAT, а где его нет?
10. Почему второй прокси не является резервным?
11. Что означает `active (exited)` у GRE-службы?
12. Что из SD-WAN, радиомоста и двух ЦОД было собрано на практике?

<summary>Короткие ответы</summary>

1. GRE упаковывает пакеты, но не даёт требуемого шифрования и аутентификации.
2. IKE согласует и поддерживает защиту/ключи; ESP защищает передаваемые данные.
3. 47 — номер протокола в IP-заголовке; TCP/UDP-порт — другое поле.
4. Туннель даёт канал, OSPF распространяет сведения об удалённых сетях.
5. Пакеты не должны уйти открытым GRE; связь пропадёт, затем OSPF удалит маршрут.
6. ICMP, TCP-порт и приложение — разные уровни и проверки.
7. Обычный запрос маршрутизируется через GRE/IPsec; SOCKS передаёт запрос приложению Xray и далее через отдельный каскад.
8. Relay завершает первый TLS-участок, HQ-GW — второй.
9. SNAT есть на BR-GW для клиента к relay TCP/443; межофисный путь GRE/IPsec не использует NAT.
10. Звенья последовательны: для успеха нужны оба, запасного обхода нет.
11. Команды oneshot выполнились, unit сохраняет активное состояние; туннель работает в ядре.
12. Это архитектурная часть; практика — пять Ubuntu, GRE/IPsec, OSPF, фильтрация, Xray и тестовый сервис.

## 20. Главная карта понятий

```text
Адреса и netplan
    ↓ дают интерфейсы и базовую достижимость
GRE
    ↓ создаёт виртуальный канал между шлюзами
IKEv2 / strongSwan
    ↓ согласует защиту
IPsec ESP / ядро Linux
    ↓ защищает GRE на WAN
OSPF / FRRouting
    ↓ изучает удалённые сети через туннель
Таблица маршрутов + ip_forward + firewall
    ↓ определяют и ограничивают пересылку
HTTP-сервис
    ↓ даёт наблюдаемый результат работы всего пути
ping, curl, show, журналы и захват
    → проверяют разные свойства, дополняя друг друга

Отдельная ветка:
Приложение → SOCKS → Xray → TLS к relay → TLS к HQ-GW → HTTP-сервис
```

Когда эта схема становится понятной, длинный абзац отчёта читается уже как набор конкретных инженерных решений: какой канал создали, чем защитили, как получили маршруты, чем ограничили доступ и какими наблюдениями подтвердили результат.
