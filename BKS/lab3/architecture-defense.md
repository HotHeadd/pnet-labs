# БКС3, вариант 6: что выбрали и почему

Это решения архитектурной части. [Схема](img/architecture.svg) показывает три сценария подключения. Два верхних блока — ЦОД, три нижних — филиалы.

## 1. Двадцать ПВЗ — SD-WAN

**Выбрали:** централизованно управляемую сеть с зашифрованными подключениями к двум ЦОД. Транспорт — доступная на точке оптика или LTE; при наличии обоих каналов один может резервировать другой. У каждого ПВЗ своя подсеть.

**Почему:** разные города и операторы, вручную обслуживать двадцать точек неудобно. SD-WAN позволяет выдавать общие настройки и политики, автоматически регистрировать устройства (ZTP) и контролировать качество каналов.

- **Плюсы:** единое управление, меньше ручной настройки, переключение при наличии запасного канала.
- **Минусы:** стоимость устройств и системы управления, зависимость от платформы; контроллеры тоже нужно резервировать.
- **Почему не другое:** QinQ требует доступной L2-услуги оператора; отдельные IPsec-туннели сами по себе не дают централизованного управления. IPsec может использоваться внутри SD-WAN для шифрования. Xray и белые IP не решают задачу управления сетью ПВЗ.

## 2. Соседняя лаборатория — радиомост + IPsec

**Выбрали:** направленный радиомост между зданиями; конфиденциальный трафик защищается IPsec.

**Почему:** кабель проложить нельзя, но есть прямая видимость. Радиомост предоставляет канал, а IPsec защищает его содержимое.

- **Плюсы:** нет межзданной кабельной прокладки, основной канал не зависит от кабельного оператора.
- **Минусы:** монтаж антенн, обследование зоны Френеля, помех и допустимых частот. Скорость и стабильность требуют расчёта и проверки; без исходных данных численные гарантии не заявляем.
- **Почему не другое:** доступность QinQ не задана; LTE имеет переменную ёмкость; Xray и белый IP не создают физический канал. Независимый операторский канал можно предусмотреть как дополнительный резерв; на обзорной схеме он не детализирован.

## 3. Подрядчик — HTTPS/mTLS через прокси в DMZ

**Выбрали:** доступ к одному веб-сервису через обратный HTTPS-прокси. mTLS проверяет сертификаты и сервера, и клиента. Межсетевой экран разрешает из DMZ только обращение к нужному сервису.

**Почему:** подрядчику нужно приложение, общий сетевой доступ к компании не нужен.

- **Плюсы:** узкий доступ, шифрование внешнего соединения, аутентификация и журналирование.
- **Минусы:** сопровождение сертификатов и прокси; резервный вход требует контроля состояния, переключения и готовой копии приложения/данных.
- **Почему не другое:** QinQ/радиомост не требуются для доступа к одному сайту; Site-to-Site VPN избыточен для этой задачи. Белый IP может дополнительно ограничивать источники, но не заменяет TLS и аутентификацию. Xray требует прокси-клиента; обычный HTTPS-вход удобнее для веб-приложения.

## Почему две DMZ

**DMZ-1 расположена в ЦОД-1, DMZ-2 — в ЦОД-2. Это два независимых сегмента, а не одна растянутая сеть.** В каждом находится свой входной прокси, отделённый от внутренних сервисов правилами межсетевого экрана (МЭ).

Основной вход подрядчика — через ЦОД-1, резервный — через ЦОД-2. Подрядчик использует одно имя сайта. Проверка доступности и DNS-переключение направляют новые подключения на резерв; это не гарантирует сохранение уже открытых сессий и требует учёта DNS-кеширования.

Дублирование DMZ — выбранное проектное решение для резервирования входа. Оно не является отдельным требованием варианта и не реализовано на практическом стенде. Репликация данных и готовность резервного сервиса нужны отдельно: два прокси сами по себе не резервируют приложение.

## Как читать схему и связать её с практикой

- Два верхних блока — основной и резервный ЦОД, три нижних — ПВЗ, лаборатория и подрядчик. Пересечения линий без узла не обозначают соединение.
- Линии без стрелок — двусторонняя связь. Стрелки — направление инициирования разрешённых запросов; ответы проходят обратно. Пунктир — резерв.
- Основные сервисы резервируются между ЦОД; для этого проект предусматривает защищённую межЦОД-связь, репликацию, независимые каналы и питание.
- В практике собраны два Linux-шлюза, GRE/IPsec и OSPF; доступ ограничен iptables. Обязательный каскад Xray отдельно показывает доступ только к `10.1.50.10:8080`.
- SD-WAN для двадцати точек, физический радиомост, две DMZ, mTLS-вход подрядчика и переключение двух ЦОД относятся к проекту. Каскад Xray не является полной реализацией этого HTTPS-входа.

**Короткий ответ на защите:** «Для ПВЗ выбрали SD-WAN ради централизованного управления, для лаборатории — радиомост с IPsec из-за невозможности кабеля, для подрядчика — HTTPS/mTLS через прокси в DMZ ради доступа только к одному приложению. На двух площадках предусмотрены отдельные основной и резервный входы».
