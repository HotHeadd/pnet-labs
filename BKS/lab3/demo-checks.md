# БКС3 — проверка на защите

Открыть `/BKS labs/BKS3.unl`, **Join к рабочей сессии 8 (`vlad_pc`)**.
Номер сессии проверять перед работой: `tools/pnet-helper.py sessions`.
В консоли Ubuntu входить как `labadmin`, пароль — в [stand/README.md](stand/README.md). `sudo` без пароля.

Команды выполнять по одной на указанной машине. Строки с `#` — комментарии, их вводить необязательно. Числа задержек, счётчики, SPI и время до обновления ключей будут меняться — это нормально. Примеры ниже поясняют структуру вывода: это не новый запуск команд. Строки с пояснениями в блоках `text` вводить не нужно.

## 1. Маршрутизация и IPsec — BR-GW и HQ-GW

На **обоих шлюзах**:

```sh
# Сосед OSPF: ищем Full в столбце State.
sudo vtysh -c 'show ip ospf neighbor'
```

Разбор команды: `sudo` — административные права; `vtysh` — консоль FRRouting; `-c` — выполнить одну команду; `show ip ospf neighbor` — показать соседей OSPF.

На **BR-GW** ожидаем соседа `10.1.254.254` с адресом `172.16.0.1` через `tun0`. На **HQ-GW** — соседа `10.2.254.254` с адресом `172.16.0.2`. `Full` (в том числе `Full/DROther`) означает сформированное соседство и синхронизацию сведений OSPF. Пустая таблица или долго сохраняющееся состояние без `Full` — повод проверить туннель и OSPF.

Пример строки на BR-GW:

```text
Neighbor ID     Pri State          Dead Time Address      Interface          RXmtL RqstL DBsmL
10.1.254.254      1 Full/DROther    7.247s   172.16.0.1   tun0:172.16.0.2      0     0     0
```

Построчно и по полям:

- Первая строка — заголовки столбцов, вторая — один сосед.
- `10.1.254.254` — Router ID шлюза офиса; это идентификатор OSPF, не следующий шлюз маршрута.
- `Pri 1` — приоритет для выбора DR в сетях, где такой выбор используется; на нашем point-to-point туннеле выбор DR не нужен.
- `Full/DROther` — соседство полностью установлено. Здесь важна часть `Full`; суффикс не означает ошибку.
- `7.247s` — сколько осталось до признания соседа недоступным, если больше не придёт Hello. После очередного Hello отсчёт обновится.
- `172.16.0.1` — реальный адрес соседа на GRE-интерфейсе.
- `tun0:172.16.0.2` — наш интерфейс и наш туннельный адрес на BR-GW.
- Три нуля в конце — нет ожидающих элементов в списках повторной передачи, запросов сведений и описания базы OSPF; при установлении соседства значения могут временно отличаться.

```sh
# Маршруты, установленные OSPF: ищем сеть другой площадки через tun0.
ip route show proto ospf
```

Разбор команды: `ip` — управление сетью Linux; `route show` — показать маршруты; `proto ospf` — оставить маршруты, установленные OSPF.

| Где выполняем | Что должно быть в строке маршрута |
|---|---|
| BR-GW | `10.1.50.0/26` через `172.16.0.1 dev tun0` |
| HQ-GW | `10.2.20.0/24` через `172.16.0.2 dev tun0` |

Маршрут получен динамически. Команда уже отфильтровала маршруты по `proto ospf`, поэтому сам текст `proto ospf` может отсутствовать в выводе. `metric` — стоимость пути, а не задержка. `nhid` и его число запоминать не нужно.

Пример строки на BR-GW:

```text
10.1.50.0/26 nhid 24 via 172.16.0.1 dev tun0 metric 20
```

- `10.1.50.0/26` — сеть назначения: LAN головного офиса.
- `nhid 24` — внутренний идентификатор объекта следующего перехода Linux.
- `via 172.16.0.1` — передать пакеты шлюзу офиса на другом конце GRE.
- `dev tun0` — отправить через туннельный интерфейс.
- `metric 20` — стоимость маршрута; меньшее значение предпочтительнее при сравнении подходящих OSPF-путей.

```sh
# Проверка согласованной защиты: ищем ESTABLISHED, INSTALLED и TRANSPORT.
sudo ipsec statusall
```

Разбор команды: `sudo` — административные права; `ipsec` — интерфейс управления strongSwan; `statusall` — подробное состояние соединений и SA.

Ищем:

- `Security Associations (1 up, 0 connecting)` — одна действующая IKE SA, нет незавершённых установлений;
- `ESTABLISHED` — служебное соединение IKE установлено;
- `INSTALLED, TRANSPORT` — защита данных установлена в транспортном режиме;
- `AES_GCM_16_256` — согласованный алгоритм ESP;
- `dynamic[gre]` или адреса с `[gre]` — защищается GRE;
- `bytes_i`, `bytes_o`, `pkts` — счётчики; после обмена они должны увеличиваться.

Основные строки вывода по порядку (служебные строки между ними опущены):

```text
Status of IKE charon daemon (strongSwan 5.9.5, ...)
```

Работает процесс IKE `charon`; далее указаны версии программы и ОС.

```text
gre-site: 203.0.113.20...203.0.113.10 IKEv2, dpddelay=10s
```

Соединение называется `gre-site`, связывает WAN-адреса филиала и офиса, использует IKEv2. `dpddelay` относится к проверке живости IKE-партнёра.

```text
local:  [203.0.113.20] uses pre-shared key authentication
remote: [203.0.113.10] uses pre-shared key authentication
```

Локальная и удалённая стороны проверяются по заранее установленному общему секрету PSK. Сам секрет здесь не выводится.

```text
child: dynamic[gre] === dynamic[gre] TRANSPORT, dpdaction=restart
```

Описание защиты данных: выбран GRE, транспортный режим, при признании соседа недоступным — попытка восстановления.

```text
Security Associations (1 up, 0 connecting)
gre-site[2]: ESTABLISHED ...
```

Первая строка — сводка активных IKE SA, вторая — конкретная установленная IKE SA. `[2]` — её внутренний номер.

```text
IKE proposal: AES_CBC_256/HMAC_SHA2_256_128/PRF_HMAC_SHA2_256/MODP_2048
```

Согласованные алгоритмы служебного обмена IKE: шифрование AES-CBC, целостность HMAC, получение ключевого материала через PRF и группа Диффи — Хеллмана MODP 2048. Это не строка алгоритма ESP.

```text
gre-site{2}: INSTALLED, TRANSPORT, reqid 1, ESP SPIs: ...
```

Защита данных установлена в ядро. `{2}` — номер CHILD SA; `reqid` связывает соответствующие состояния/политики; SPI — идентификаторы ESP для двух направлений.

```text
AES_GCM_16_256, 1176 bytes_i (16 pkts, ...), 1176 bytes_o (16 pkts, ...), rekeying in 43 minutes
```

AES-GCM защищает данные, тег проверки — 16 байт, ключ — 256 бит. `i` — принято, `o` — отправлено относительно этого шлюза; `pkts` — количество пакетов. Конец строки показывает оставшееся время до планового обновления ключей.

```text
203.0.113.20/32[gre] === 203.0.113.10/32[gre]
```

Селекторы: защита применяется к GRE между двумя конкретными WAN-адресами. Это не обещание шифровать вообще любой трафик этих машин.

Номера SA и SPI могут отличаться от отчёта. Во время обновления возможны временные дополнительные SA. Установленная SA сама по себе ещё не доказывает доступность сайта — это проверяем ниже.

**Что сказать:** «Шлюзы установили OSPF-соседство и автоматически получили удалённые сети. Между ними установлена защита GRE через IPsec».

## 2. Обычный путь через туннель — BR-CLIENT

```sh
# Выбранный маршрут: через шлюз филиала, с адреса клиентской LAN.
ip route get 10.1.50.10
```

Ожидаем:

```text
10.1.50.10 via 10.2.20.1 dev ens3 src 10.2.20.42 ...
```

`10.1.50.10` — запрошенная цель; `via 10.2.20.1` — следующий шлюз; `dev ens3` — выходной интерфейс; `src 10.2.20.42` — выбранный исходный адрес. Если ниже есть `cache`, это служебная пометка результата поиска маршрута. Здесь не должно быть служебного адреса `192.168.15.*` или служебного шлюза `192.168.15.2`. Это проверка выбранного маршрута, а не доставки пакета.

```sh
# Проверка ICMP: четыре запроса с адреса филиала.
ping -I 10.2.20.42 -c 4 10.1.50.10
```

Разбор команды: `-I 10.2.20.42` — исходный адрес; `-c 4` — четыре запроса; последний адрес — цель.

Пример ответа:

```text
64 bytes from 10.1.50.10: icmp_seq=1 ttl=62 time=5.01 ms
```

- `64 bytes` — размер ICMP-ответа, не всего внешнего пакета GRE/IPsec.
- `from 10.1.50.10` — кто ответил.
- `icmp_seq=1` — номер запроса, на который пришёл ответ.
- `ttl=62` — оставшийся TTL ответного пакета; это ограничитель числа переходов, не задержка.
- `time=5.01 ms` — время туда и обратно для этой пробы.

Итоговые строки:

```text
4 packets transmitted, 4 received, 0% packet loss
rtt min/avg/max/mdev = ... ms
```

Первая — отправлено, получено, доля потерь. Вторая — минимальное, среднее, максимальное время туда-обратно и разброс времени ответов.

Ожидаем четыре ответа `bytes from 10.1.50.10`, итог `4 transmitted, 4 received` и `0% packet loss`. Значения `time` меняются. Параметр `-I` фиксирует исходный адрес, чтобы не проверить случайно служебный путь.

```sh
# Проверка TCP/8080 и ответа приложения через туннель.
curl --max-time 8 --interface 10.2.20.42 http://10.1.50.10:8080
```

Разбор команды: `curl` — HTTP-клиент; `--max-time 8` — ограничить всю операцию восемью секундами; `--interface 10.2.20.42` — использовать исходный адрес LAN; `http://` — обычный HTTP; `:8080` — порт сервиса.

Ожидаем строку:

```text
BKS3: protected HQ service
```

Это подтверждает, что прошёл TCP-обмен и ответил веб-сервис. Здесь нет SOCKS-параметра: проверяется обычный маршрут через GRE/IPsec.

```sh
# Путь до сервера: шлюз филиала → шлюз офиса → сервер.
traceroute -n -I -m 6 -w 1 10.1.50.10
```

Разбор команды: `-n` — не искать DNS-имена; `-I` — использовать ICMP (у traceroute это не выбор источника, как у ping); `-m 6` — максимум шесть переходов; `-w 1` — ждать ответ на пробу одну секунду.

Ожидаем последовательность:

```text
1  10.2.20.1
2  172.16.0.1
3  10.1.50.10
```

Строка `1` — первый переход, BR-GW; `2` — туннельный адрес HQ-GW; `3` — конечный сервер. Числа в `ms` после адреса — время отдельных проб до этого перехода и обратно.

В строках могут присутствовать `*`: отдельная проба не получила ответа за отведённое время. Если конечный сервер достигнут, отдельные звёздочки не означают отказ всего пути. Служебная сеть `192.168.15.*` в проверяемом пути не участвует.

```sh
# Проверка MTU: внутренний IPv4-пакет 1400 байт без фрагментации.
ping -M do -s 1372 -I 10.2.20.42 -c 3 10.1.50.10
```

Разбор команды: `-M do` — запретить фрагментацию; `-s 1372` — размер данных ICMP; `-I` — исходный адрес; `-c 3` — число запросов.

В выводе `1372(1400)` означает 1372 байта данных и 1400 байт внутреннего IPv4-пакета. В строке ответа может быть `1380 bytes`: это данные с заголовком ICMP, без IPv4-заголовка.

Ожидаем `1372(1400) bytes of data`, три ответа и `0% packet loss`. 1372 байта данных + 8 байт ICMP + 20 байт IPv4 = 1400 байт. `-M do` запрещает фрагментацию. Ошибка `message too long` или отсутствие ответов требуют проверки размера и пути. Этот тест подтверждает проходимость 1400 байт, но не определяет максимальный возможный MTU.

**Что сказать:** «Клиент из LAN филиала достигает сервера через оба шлюза. Работают ICMP, HTTP и передача пакета размером 1400 байт без фрагментации».

## 3. Шифрование на внешнем канале — хост PNETLab

**Эти команды выполняются на сервере PNETLab, не внутри Ubuntu-узлов.** Нужен SSH-доступ к хосту `100.100.57.19`.

```sh
# Найти WAN-мост текущей сессии.
brctl show
```

В выводе `bridge name` — имя виртуального коммутатора Linux; `bridge id` — его идентификатор; `STP enabled` — включён ли протокол защиты от петель; `interfaces` — подключённые интерфейсы. Строки без повторения имени моста продолжают список его портов.

Для сессии 8 WAN-мост — `vnet8_1`. В проверенной топологии к нему подключены `vunl63_0`, `vunl64_0`, `vunl67_0` — WAN шлюзов и relay. При смене сессии имя моста перепроверить.

```sh
# Показывать ESP (протокол 50) и открытый GRE (протокол 47).
sudo tcpdump -nn -i vnet8_1 'ip proto 50 or ip proto 47'
```

Разбор команды: `tcpdump` — захват пакетов; `-nn` — показывать числовые адреса и порты; `-i vnet8_1` — выбранный интерфейс; выражение в кавычках — фильтр «ESP или GRE». `sudo` даёт права захвата.

Оставить захват работающим. **На BR-CLIENT в другой консоли** повторить:

```sh
ping -I 10.2.20.42 -c 4 10.1.50.10
```

В захвате ожидаем строки вида:

```text
IP 203.0.113.20 > 203.0.113.10: ESP(spi=...,seq=...), length ...
IP 203.0.113.10 > 203.0.113.20: ESP(spi=...,seq=...), length ...
```

В каждой строке захвата:

- `IP` — пакет IPv4.
- Адрес слева от `>` — отправитель, справа — получатель.
- `ESP` — пакет защищён механизмом ESP.
- `spi` — идентификатор состояния защиты на принимающей стороне.
- `seq` — порядковый номер ESP-пакета, используемый в том числе для защиты от повторного воспроизведения.
- `length` — длина ESP-части, отображаемая tcpdump, не размер HTTP-страницы.

Ищем **ESP в обоих направлениях и отсутствие строк открытого GRE**. Если вообще ничего не видно, сначала проверить выбранный мост и наличие тестового трафика. Номер 50 — IP-протокол, не порт. Захват ограничен указанным фильтром: он не показывает весь WAN-трафик.

Остановить `tcpdump` клавишами **Ctrl+C**. Для остановки захвата не останавливать узлы.

**Что сказать:** «Наблюдаем трафик снаружи гостевых ОС: между WAN-адресами идёт ESP, исходный GRE в открытом виде в этом захвате отсутствует».

## 4. Отдельный путь через каскад Xray

На **BR-CLIENT**:

```sh
# Разрешённая цель через локальный SOCKS и два прокси-перехода.
curl --max-time 8 --socks5-hostname 127.0.0.1:1080 http://10.1.50.10:8080
```

Разбор команды: `--max-time 8` — общий лимит времени; `--socks5-hostname 127.0.0.1:1080` — отправить запрос локальному SOCKS5-прокси (разрешение имён цели, если оно нужно, поручается прокси); последний URL — конечный сервис.

Ожидаем тот же ответ `BKS3: protected HQ service`. Теперь наличие `--socks5-hostname` означает обращение к локальному Xray; это отдельный путь через relay, а не обычный запрос по туннельному маршруту.

```sh
# Запрещённая цель: тот же сервер, но порт SSH вместо разрешённого 8080.
curl --max-time 4 --socks5-hostname 127.0.0.1:1080 http://10.1.50.10:22
# Выполнить сразу после curl: посмотреть код его завершения.
echo $?
```

В отрицательной команде `:22` — запрещённый порт назначения, остальной путь к прокси тот же. `echo` печатает значение, `$?` — код завершения непосредственно предыдущей команды: `0` означает успешное завершение curl, ненулевой код — ошибку. Между curl и `echo $?` не выполнять другие команды.

Ожидаем ошибку и ненулевой код. В последней проверке было `curl: (52) Empty reply from server`, код `52`; формулировка и код могут отличаться. Это намеренно отрицательная проверка — ошибка здесь ожидаема. Сам по себе неуспех curl ещё не доказывает причину: ограничение подтверждается также правилами Xray, а доступность разрешённой цели — предыдущим успешным запросом.

На **XRAY-RELAY**, затем на **HQ-GW**:

```sh
# Ищем свежую запись именно от только что выполненного запроса.
sudo tail -n 5 /var/log/xray/access.log
```

Ожидаем:

```text
XRAY-RELAY: from 203.0.113.20:... accepted tcp:10.1.50.10:8080 [entry -> next]
HQ-GW:     from 203.0.113.30:... accepted tcp:10.1.50.10:8080 [entry -> next]
```

Разбор команды журнала: `tail` — показать конец файла; `-n 5` — последние пять строк; путь — журнал доступа Xray. В записи `from` — непосредственный отправитель соединения, число после двоеточия — его временный исходный порт; `accepted tcp:10.1.50.10:8080` — принятая TCP-цель; `[entry -> next]` — метки входа и выбранного выхода Xray.

Первая запись показывает приём от BR-GW после SNAT, вторая — приём от relay. Сверять время: старые записи не подтверждают сегодняшний запрос. Наличие свежей записи на обоих узлах подтверждает два последовательных перехода.

Дополнительно на **BR-CLIENT**:

```sh
# SOCKS должен слушать только локальный адрес.
ss -lnt | grep ':1080'
```

Разбор команды: `ss` — показать сокеты; `-l` — слушающие; `-n` — числовые адреса/порты; `-t` — TCP. Символ `|` передаёт вывод следующей программе, `grep` оставляет строки с `:1080`.

В выводе `State` — состояние; `Recv-Q` и `Send-Q` — параметры очередей; `Local Address:Port` — где слушает наша программа; `Peer Address:Port` — другая сторона (для слушающего сокета обычно общий шаблон).

Ожидаем `LISTEN` и `127.0.0.1:1080`. Адрес `0.0.0.0:1080` в столбце локального адреса означал бы публикацию входа на всех IPv4-интерфейсах. Не путать локальный адрес со столбцом адреса другой стороны, где `0.0.0.0:*` нормально.

**Что сказать:** «Приложение использует локальный SOCKS. Запрос проходит через relay и шлюз офиса, но разрешён только один адрес и порт».

## 5. Отказ и восстановление — необязательная демонстрация

Согласовать с работающими в той же сессии: команды временно нарушают связь. Для обычного показа достаточно пунктов 1–4. После каждого эксперимента обязательно выполнить восстановление.

### 5.1. Отказ IPsec

На **BR-GW**:

```sh
sudo systemctl stop strongswan-starter
```

Построчно: `sudo` — права администратора; `systemctl` — управление службами; `stop` — остановить сейчас; `strongswan-starter` — служба IPsec. Успешная команда обычно ничего не печатает. Она не удаляет конфиг и не отключает автозапуск.

На **BR-CLIENT**:

```sh
ping -I 10.2.20.42 -c 3 -W 1 10.1.50.10
```

`-W 1` у ping — ожидание ответа одну секунду; это не OSPF-таймер и не срок обнаружения отказа DPD. Остальные параметры разобраны в пункте 2.

Ожидаем отсутствие ответов (`100% packet loss`); возможна ошибка недоступности. На **BR-GW** после истечения OSPF dead interval (около 8 секунд без Hello):

```sh
ip route show proto ospf
```

Маршрут к `10.1.50.0/26` должен исчезнуть. GRE-интерфейс может остаться `UP` — это не означает работающую связь. На WAN открытый GRE появляться не должен: firewall блокирует незащищённую передачу.

**Восстановить на BR-GW:**

```sh
# 1. Запустить службу IPsec; отсутствие текста обычно нормально.
sudo systemctl start strongswan-starter
# 2. Убедиться, что IKE и защита данных снова установлены.
sudo ipsec statusall
# 3. Проверить восстановление OSPF-соседства до Full.
sudo vtysh -c 'show ip ospf neighbor'
# 4. Проверить возврат маршрута к удалённой LAN.
ip route show proto ospf
```

Дождаться `ESTABLISHED`, `INSTALLED`, `Full` и возврата маршрута. Затем повторить ping и обычный curl с клиента: они должны снова работать.

### 5.2. Отказ промежуточного Xray

На **XRAY-RELAY**:

```sh
sudo systemctl stop xray
```

`stop xray` останавливает только прокси на этой машине. Успешная остановка обычно не сопровождается текстом; это не выключение Ubuntu.

На **BR-CLIENT**:

```sh
curl --max-time 8 --socks5-hostname 127.0.0.1:1080 http://10.1.50.10:8080
```

Ожидаем ошибку вместо строки сервиса. Каскад зависит от relay и не имеет обходного перехода. Обычный путь через GRE/IPsec при работающей защите от этого не должен ломаться.

**Восстановить на XRAY-RELAY:**

```sh
# Запустить прокси на relay.
sudo systemctl start xray
# Узнать текущее состояние службы.
systemctl is-active xray
```

Ожидаем `active`. Повторить SOCKS-запрос с клиента: снова должна появиться строка сервиса.

## Перед завершением

На каждом узле можно проверить:

```sh
systemctl --failed --no-pager
```

Разбор команды: `systemctl` — менеджер служб; `--failed` — показать только ошибочные unit; `--no-pager` — вывести сразу в терминал без отдельного просмотрщика. Заголовок `UNIT LOAD ACTIVE SUB DESCRIPTION` перечисляет имя, загрузку определения, общее состояние, подробное состояние и описание.

Ожидаем `0 loaded units listed` — нет служб в состоянии failed. Это не заменяет проверку нужных служб и обмена: остановленная вручную служба может не считаться ошибочной.

После демонстрации обычный HTTP и HTTP через SOCKS должны работать. Все пять узлов оставить запущенными. Лабу и чужие сессии не останавливать.
