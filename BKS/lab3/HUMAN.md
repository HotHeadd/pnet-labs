# Как устроена БКС3

Отчёт — `main.pdf`, исходник — `main.typ`, методичка — `preamble/`.
Рабочая лаба `/BKS labs/BKS3.unl`, сценарий защиты — `demo-checks.md`.

Вариант 6: двадцать ПВЗ получают SD-WAN с централизованной настройкой; соседняя
лаборатория — радиомост; подрядчик — доступ к одному веб-сервису через прокси в DMZ.
Это архитектурная часть, не двадцать виртуальных ПВЗ в эмуляторе.

В практической части два Ubuntu-шлюза связывают LAN филиала и серверную LAN ГО.
GRE переносит исходные IP-пакеты и multicast OSPF, IPsec шифрует GRE, FRRouting
автоматически объявляет локальные сети. Данные идут без межофисного NAT.

Путь HTTP: `10.2.20.42 → BR-GW → GRE/IPsec → HQ-GW → 10.1.50.10:8080`.
Путь каскада: `SOCKS на BR-CLIENT → TLS/443 XRAY-RELAY → TLS/443 HQ-GW → сервер`.
Разрешён только конкретный адрес и порт; SSH и другие подсети через каскад закрыты.
Каскад добавляет переходы и точки отказа, поэтому не является резервированием.

Связь с прошлыми работами: сохранены адреса ГО `10.1.0.0/16`, филиала `10.2.0.0/16`,
сервер `10.1.50.10/26` и клиент `10.2.20.42/24`. В БКС1 GRE/IPsec выполняли Cisco,
в БКС2 Ubuntu защищала DMZ и обслуживала удалённого пользователя через WireGuard.
БКС3 демонстрирует Linux Site-to-Site. Предыдущие стенды не изменены.

Служебные интерфейсы `192.168.15.211–215` нужны для управления и загрузки пакетов.
Они не являются VPN-транспортом. Удалённые LAN объявлены только через tun0,
а FORWARD через интерфейсы управления закрыт.

После остановки IPsec открытый GRE отбрасывается, соседство OSPF истекает и маршрут
удаляется. После запуска служб всё восстанавливается автоматически.
