## 1. Схема за две минуты

**Идея.** В ЛР1 в сеть головного офиса (ГО) были вставлены межсетевые экраны «прозрачным мостом» без правил —
разработку политик отложили на следующие ЛР. ЛР2 и есть эта следующая работа: на месте МЭ перед DMZ стоит
Ubuntu Server с iptables, он же VPN-сервер. Стенд — не вся сеть ЛР1, а её фрагмент с **теми же адресами**.

```
EXT-CLIENT (Kali, «внешний сотрудник»)  203.0.113.18
      │
     ISP (8.8.8.8 = «интернет», Loopback0)
      │ 203.0.113.0/30
   HQ-EDGE (граница ГО, NAT для ADMIN) ── PC-HQ-ADMIN (сеть администраторов 10.1.10.0/27)
      │ 203.0.113.8/29 — публичная сеть, её «выдал» провайдер
   HQ-FW (Ubuntu 22.04: iptables + WireGuard)      ens5 ── облако управления (apt, SSH)
      │ 10.1.100.0/28 — DMZ
   HQ-DMZ (коммутатор, VLAN 100)
      │
   WIN-SRV (Windows Server 2019, 10.1.100.12: RDP + IIS)
```

**Как рассказывать — по пути пакета:**

1. Провайдер маршрутизирует ГО публичную сеть 203.0.113.8/29. На HQ-EDGE она **не транслируется** — поэтому
   NAT для DMZ делает сам МЭ, и у него есть «белые» адреса: .10 (сам МЭ, VPN, публикация) и .11 (адрес WIN-SRV наружу).
2. HQ-FW — шлюз DMZ. Всё, что входит в DMZ и выходит из неё, проходит через его цепочку FORWARD.
3. Внешний сотрудник подключается к МЭ по WireGuard (udp/51820 на 203.0.113.10), получает адрес 10.1.200.8 и
   через туннель открывает RDP к WIN-SRV. Без туннеля до WIN-SRV не добраться: RDP не опубликован.
4. Сканер из интернета видит не реальные порты МЭ, а «все открыты» (TARPIT) — и не может понять, что там на самом деле.

## 3. Как это работает

### 3.1. Политика iptables (`commands/HQ-FW-iptables.sh`)

- **«Запрещено всё, что не разрешено»:** политика INPUT и FORWARD = DROP. OUTPUT = ACCEPT (МЭ сам себе доверяет).
- **conntrack (трассировка соединений):** `ESTABLISHED,RELATED` пропускается в начале цепочек — ответы на
  разрешённые соединения не надо разрешать отдельными правилами; `INVALID` (пакеты вне соединения) отбрасывается.
- **Порядок важен:** правила проверяются сверху вниз до первого совпадения, поэтому защита от сканирования стоит
  в INPUT **до** разрешений.
- **Цепочки:**
  - INPUT — трафик к самому МЭ: WireGuard с WAN; SSH только из сети управления и из ADMIN ГО; ping с ограничением с WAN;
  - FORWARD — транзит: DMZ → только в интернет (во внутренние 10.0.0.0/8 — запрет с записью в журнал); из интернета
    в DMZ — только то, что прошло DNAT (веб); из VPN — только RDP и ping к WIN-SRV; из ADMIN — ping и HTTP в DMZ.
- **LOG_DROP:** перед отбрасыванием пакет пишется в журнал ядра с префиксом `FW-DROP:`, но не чаще 10 раз
  в минуту — чтобы атакой нельзя было забить журнал.
- **Сохранение:** `netfilter-persistent save` → `/etc/iptables/rules.v4`, правила поднимаются после перезагрузки.

### 3.2. NAT — четыре разновидности на МЭ + одна на HQ-EDGE

| Вид | Где | Зачем |
|---|---|---|
| **SNAT** (`--to-source 203.0.113.11`) | POSTROUTING, источник WIN-SRV | у сервера свой постоянный внешний адрес — удобно для белых списков у партнёров |
| **MASQUERADE** | POSTROUTING, остальная DMZ | то же, но адрес берётся с интерфейса (подходит, когда внешний адрес может меняться) |
| **DNAT — проброс порта** | PREROUTING, 203.0.113.10:8080 → 10.1.100.12:80 | публикация веб-сервера IIS из DMZ в интернет |
| **DNAT — перенаправление** | PREROUTING, udp/53 из DMZ → 8.8.8.8 | серверы DMZ не могут ходить к «чужим» DNS — только к корпоративному резолверу |
| **PAT (overload)** | HQ-EDGE, сеть ADMIN | обычный выход офисных ПК в интернет через один адрес |

SNAT и MASQUERADE — это оба «source NAT»; разница — в фиксированном адресе и в том, что MASQUERADE при смене
адреса интерфейса сбрасывает соединения.

### 3.3. DMZ

DMZ (демилитаризованная зона) — сегмент для серверов, доступных извне. Принцип: **из интернета в DMZ — только
опубликованное, из DMZ во внутреннюю сеть — ничего.** Если WIN-SRV взломают, атакующий не попадёт в сеть ГО.
Проверка: `ping 10.1.10.10` с WIN-SRV — тайм-аут, в журнале МЭ `FW-DROP: IN=ens4 ... DST=10.1.10.10`.
В обратную сторону администраторы ГО ходят в DMZ (ping, HTTP) — разрешено правилом из ADMIN.

### 3.4. WireGuard (`commands/HQ-FW-wireguard.sh`)

- VPN уровня ядра, UDP. Криптография фиксированная, без «согласования»: Curve25519 (обмен ключами),
  ChaCha20-Poly1305 (шифрование и целостность), BLAKE2s (хеш). Нечего «понизить» — нет атак отката версии.
- Аутентификация — по открытым ключам: сервер знает открытый ключ клиента, клиент — сервера.
- **AllowedIPs** работает в обе стороны: на сервере `10.1.200.8/32` — от этого клиента принимаются пакеты только
  с этим адресом (подмена адреса внутри туннеля невозможна); на клиенте `10.1.200.0/24, 10.1.100.12/32` —
  в туннель уходит только трафик к VPN и к WIN-SRV (split tunnel), интернет клиента идёт мимо.
- WireGuard «молчит»: на пакет без правильного ключа он не отвечает, поэтому порт 51820 сканером не виден.
- На Kali 2019.3 ядро 5.3 без модуля WireGuard → собрана userspace-реализация `wireguard-go`; протокол тот же.

### 3.5. RDP + NLA

- **NLA (Network Level Authentication)** — пользователь вводит логин и пароль **до** того, как сервер создаст сеанс
  и покажет экран входа (протокол CredSSP). Без NLA любой, кто достучался до 3389, получает экран входа Windows
  и тратит ресурсы сервера; через это эксплуатировались уязвимости вроде BlueKeep (CVE-2019-0708).
- `UserAuthentication=1` — требовать NLA; `SecurityLayer=2` — канал только TLS (не «RDP Security Layer»).
  Заданы и в реестре службы, и групповой политикой, чтобы их нельзя было сбросить локальной настройкой.
- Брандмауэр Windows: встроенные правила RDP выключены, 3389 разрешён **только с 10.1.200.0/24** — даже если
  кто-то окажется в DMZ, к RDP он не подключится. Это вторая линия защиты после МЭ.
- Для работы — отдельный пользователь `rdpuser` без прав администратора (группа Remote Desktop Users).
- Проверка: nmap `rdp-enum-encryption` показывает только CredSSP (NLA) и RDSTLS; `xfreerdp /sec:rdp` (без NLA) —
  `Protocol Security Negotiation Failure`.

### 3.6. Защита от сканирования (xtables-addons)

xtables-addons — набор дополнительных модулей netfilter, собирается DKMS под ядро.

- **psd** (Port Scan Detection, из xtables-addons): у каждого источника считается «вес» обращений к разным портам
  (порты < 1024 — 3, остальные — 1). Порог 21 за 3 с (`--psd-delay-threshold 300` — в сотых долях секунды) →
  пакет в цепочку PORTSCAN.
- **recent** (стандартный модуль): больше 20 попыток TCP-соединения к МЭ за 60 с с одного адреса → PORTSCAN.
  Это страховка от медленного сканирования, которое не набирает вес psd.
- **PORTSCAN:** запись в журнал (`FW-PORTSCAN:`), затем **TARPIT** (из xtables-addons): МЭ отвечает SYN-ACK
  с окном TCP 0. Сканер видит «порт открыт», а передать данные не может; соединение висит, ресурсы
  тратит сканер, а не сервер (TARPIT не хранит состояние). Итог — nmap показывает открытыми **все** порты.
- **DELUDE** (из xtables-addons) на порту-ловушке 12345: на SYN отвечает SYN/ACK, на остальное — RST. Сканер
  (полуоткрытое сканирование `-sS`) считает порт открытым — имитация сервиса (netbus), которого нет.
- **Исправление TTL:** в xtables-addons 3.19 на ядре 5.15 DELUDE формирует ответ с TTL = 0, и первый же
  маршрутизатор (HQ-EDGE) его выбрасывает — nmap видел `filtered`. Правило
  `-t mangle -A POSTROUTING -o ens3 -m ttl --ttl-eq 0 -j TTL --ttl-set 64` чинит это, теперь 12345 — `open`.
  Хороший ответ на вопрос «что было сложного».

### 3.7. SSH к МЭ (`commands/HQ-FW-hardening.sh`)

Только пользователь `fwadmin`, только по ключу Ed25519, root и пароли запрещены, `MaxAuthTries 3`; разрешены
только современные алгоритмы (Curve25519, ChaCha20-Poly1305/AES-256-GCM, HMAC-SHA2-ETM); проброс портов и
X11 выключены; баннер о логировании. На уровне МЭ — SSH только из сети управления и ADMIN ГО, не больше двух
одновременных сессий с адреса (connlimit). fail2ban банит адрес на час после 3 неудачных попыток за 10 минут.
`sudo` — с паролем: украденного ключа недостаточно для прав root.

### 3.8. Резервное копирование и масштабируемость

- **etckeeper** — /etc в git: каждое изменение (в т. ч. установка пакетов) — коммит; можно сравнить и откатить.
- **hq-fw-backup** (cron, 02:30 ежедневно) — архив правил МЭ, WireGuard, SSH, netplan, sysctl, fail2ban,
  auditd в `/var/backups/hq-fw`, хранятся последние 14.
- **Повторяемость:** вся настройка — скрипты в `commands/`; второй МЭ поднимается их запуском.
- **Масштабирование:** новый VPN-клиент — ещё один `[Peer]`; отказоустойчивость — второй МЭ с keepalived (VRRP)
  и conntrackd (синхронизация таблицы соединений) — это в сравнительном анализе.

### 3.9. Уязвимости, бэкдоры, доп. защита

- `apt full-upgrade` при установке + **unattended-upgrades** (ежедневные обновления безопасности).
- **Lynis** — аудит настроек: индекс защищённости 65 → 71.
- **rkhunter, chkrootkit** — поиск руткитов и бэкдоров: 0 найдено. Предупреждения rkhunter о `/etc/.git` — это
  etckeeper (добавлены в исключения); chkrootkit ругается на тестовые файлы fail2ban — ложные срабатывания.
- **Ревизия сервисов:** `ss -tulpn` — наружу слушают только SSH и WireGuard; snapd, multipathd, ModemManager
  выключены.
- **auditd** — журнал изменений файлов правил МЭ, WireGuard, SSH, netplan и запуска iptables.
- **sysctl:** rp_filter (защита от подмены адреса), запрет ICMP redirect и source routing, SYN cookies
  (защита от SYN-флуда), журнал «марсианских» пакетов; IPv6 на МЭ закрыт.

## 4. Вопросы, которые могут задать

**Почему Ubuntu/iptables, а не pfSense, как в ЛР1?** Вариант требует xtables-addons (psd, TARPIT, DELUDE) —
это расширения netfilter Linux, на FreeBSD их нет. Плюс WireGuard в ядре, правила — текст в git,
LTS-поддержка. Таблица сравнения — в разделе 3 отчёта.

**iptables или nftables?** В Ubuntu 22.04 команда `iptables` — это `iptables-nft`: синтаксис iptables,
выполнение на движке nftables. Модули xtables-addons подключаются через совместимость xt.

**Чем DROP отличается от REJECT?** DROP молча отбрасывает (сканер ждёт тайм-аута и видит «filtered»), REJECT
отвечает отказом (RST или ICMP unreachable — быстро, но раскрывает, что хост есть).

**Почему TARPIT, а не просто DROP?** DROP говорит сканеру «тут МЭ», TARPIT превращает результат в мусор
(«открыто всё») и замедляет сканирование.

**Не заблокирует ли защита от сканирования легальных пользователей?** Она стоит только на INPUT с WAN, т. е.
на соединения к самому МЭ. Веб-сервер через DNAT идёт по FORWARD и не считается; VPN — один UDP-порт, вес psd мал.

**Что будет, если украдут ключ WireGuard?** Удалить `[Peer]` клиента на сервере — доступ пропадёт. Но и с
ключом атакующий получит только RDP к WIN-SRV, где ещё нужен пароль (NLA).

**Почему ключ клиента сгенерирован на сервере?** Так проще на стенде. Конфиг передан по изолированной сети
управления, ключ с МЭ удалён. По-хорошему клиент генерирует пару сам и отдаёт только открытый ключ.

**Как Windows выходит в интернет?** Шлюз 10.1.100.1 (МЭ) → SNAT в 203.0.113.11 → HQ-EDGE → ISP. tracert:
10.1.100.1 → 203.0.113.9 → 8.8.8.8.

**Почему без туннеля нельзя на RDP?** (1) 10.1.100.0/28 из интернета не маршрутизируется — провайдер знает
только 203.0.113.8/29; (2) для 3389 на 203.0.113.10 нет DNAT; (3) в FORWARD RDP разрешён только из wg0;
(4) брандмауэр Windows пускает 3389 только из 10.1.200.0/24.

**Как встроить в полную сеть ЛР1?** Прозрачный pfSense перед DMZ заменяется маршрутизирующим МЭ: на HQ-EDGE —
маршруты в DMZ и VPN через МЭ, ACL DMZ на HQ-EDGE больше не нужны — их роль выполняет FORWARD МЭ.

## 5. Честно об ограничениях стенда

- «Интернет» — Loopback 8.8.8.8 на ISP: ping и трассировка работают, **настоящего DNS там нет**. DNAT DNS
  показан счётчиком правила, а не разрешением имён.
- Обновления из WAN стенда не скачать (нет реального интернета); пакеты ставились через облако управления.
  unattended-upgrades настроены и заработают в реальной сети.
- В методичке порт с DELUDE показан как `filtered` — это как раз симптом бага с TTL = 0 (см. 3.6); после
  исправления — `open`, как и описано в документации xtables-addons.
- Kali после перезагрузки: туннель поднимать вручную (`wg-quick up wg0`).
