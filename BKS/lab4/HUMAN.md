# БКС4 — гайд к защите, вариант 6

Здесь — устройство стенда, смысл настроек и объяснения для защиты. Отчёт — `main.pdf`, исходник — `main.typ`, условие — `preamble/`. Команды полного прогона собраны в [demo-checks.md](demo-checks.md), сведения о запуске — в [stand/README.md](stand/README.md).

## 1. Идея лабы за две минуты

Мы сравниваем два межсетевых экрана нового поколения: Kerio Control и «Континент 4». Обычный МЭ разрешает или запрещает соединения по адресам, протоколам и портам. NGFW дополнительно распознаёт приложения, проверяет файлы антивирусом и ищет признаки атак в трафике.

Обе платформы поочерёдно занимают место одного шлюза между четырьмя сетями. Так сравниваются одинаковые клиенты, серверы и воздействия. Вариант 6: опубликовать веб-сервер в DMZ, запретить гостям мессенджеры и файлообмен при сохранении доступа администратора, сравнить доступ с GeoIP и без него.

Короткий рассказ: «На общей топологии я настроил две платформы с запретом по умолчанию. Проверил публикацию DMZ, изоляцию сетей, HTTP-антивирус, групповой контроль приложений, IDS/IPS и GeoIP. Решения шлюза сопоставляю с клиентским результатом и журналом; события отправляются на отдельный АРМ».

## 2. Схема и адреса

```text
WAN-TEST 192.168.100.1
           |
  WAN шлюза 192.168.100.2
   KERIO или CONTINENT
       /        |         \
     LAN       DMZ      Management
 10.1.10.1  10.1.50.1   10.1.99.1
     |          |          |       \
LAN-CLIENT   DMZ-WEB    ADMIN-LINUX ADMIN-WIN
10.1.10.42  10.1.50.10  10.1.99.10 10.1.99.20
```

| Сегмент | Подсеть | Назначение |
|---|---|---|
| WAN | 192.168.100.0/24 | Внешний тестер, выход через WAN-TEST, публикация сервера |
| LAN | 10.1.10.0/24 | Гостевой клиент |
| DMZ | 10.1.50.0/26 | nginx с HTTP/HTTPS и тестовыми файлами |
| Management | 10.1.99.0/24 | Управление NGFW, журналы, мониторинг и ICAP |
| OOB | Служебная сеть 192.168.15.0/24 | SSH и обслуживание виртуальных машин |

OOB обходит исследуемый путь, поэтому проверки привязываются к рабочему адресу источника. Например, `curl --interface 10.1.10.42` отправляет запрос от LAN-клиента.

У Kerio и Континента одинаковые адреса шлюзов. Одновременно их включать нельзя: возникнет конфликт IP и ARP. Рабочая лабораторная — `/BKS labs/BKS4.unl`; присоединение к существующей сессии — через Join.

## 3. Как проходит пакет

**LAN → DMZ:** `10.1.10.42 → 10.1.10.1 → 10.1.50.10:80/443`. HTTP и HTTPS разрешены, SSH из LAN запрещён. Между внутренними сетями адрес источника сохраняется.

**LAN → WAN:** клиент идёт через NGFW к `192.168.100.1`. SNAT заменяет внутренний адрес источника на WAN-адрес шлюза `192.168.100.2`. WAN-TEST обеспечивает дальнейший выход из стенда.

**WAN → DMZ:** тестер обращается к `192.168.100.2:8080` или `:8443`. DNAT переводит назначение в `10.1.50.10:80` или `:443`. Внешний клиент использует адрес публикации, а обслуживает запрос nginx в DMZ.

**Management → DMZ:** администратору разрешены веб-доступ и SSH. **DMZ → LAN:** инициирование соединения запрещено, чтобы компрометация публичного сервера не открывала внутреннюю сеть.

NAT меняет адреса и порты; разрешение соединения задаёт политика МЭ. Сам по себе проброс порта не заменяет разрешающее правило.

## 4. Политика и различия платформ

Правила обрабатываются сверху вниз. Сначала идут необходимые исключения и разрешения, затем запреты; остальной трафик отбрасывается с журналированием.

В «Континенте» отдельные таблицы МЭ и NAT. Правило входящей публикации описывает исходное назначение до DNAT — `192.168.100.2:8080/8443`. Для внутренних обменов используется NoNAT, для выхода — SNAT. Политика хранится в ЦУС и отдельно устанавливается на узел безопасности. ADMIN-WIN с Менеджером конфигурации и CSP служит АРМ управления.

В Kerio NAT задаётся в самих правилах трафика. Управление выполняется через WebAdmin; изменения API закрепляются подтверждением конфигурации. После изменения IPS движку нужно время для запуска.

Управление разрешено из Management: Kerio — HTTPS 4081, API ЦУС — 444. Для API Континента нужен клиент с поддержкой ГОСТ. Ошибка TLS обычного curl сама по себе ничего не говорит о правиле доступа.

## 5. Антивирус: что именно проверяем

EICAR — безвредный стандартный тестовый файл для проверки реакции антивируса. Используем исходный файл, ZIP с ним и обычный `allowed.txt` для контроля доступности.

В «Континенте» HTTP-профиль отправляет ответ сервера на ICAP `10.1.99.10:1344`; c-icap передаёт содержимое ClamAV. Режим RESPMOD означает проверку ответа, fail-closed — запрет передачи при недоступности проверки. Профиль назначен HTTP-правилам LAN и Management.

Kerio использует встроенный антивирус. При EICAR он может успеть вернуть HTTP-заголовок 200, затем сбросить соединение. Поэтому смотрим также число полученных байт: тело 0 байт и нативное событие EICAR подтверждают результат. «Континент» возвращает страницу блокировки с кодом 403.

По HTTPS без TLS-инспекции передаются 68 байт EICAR: содержимое зашифровано. Для анализа файла шлюзу пришлось бы завершать TLS и устанавливать новое соединение, а клиентам — доверять его центру сертификации. В этой схеме TLS-инспекция не используется.

## 6. Группы и распознавание приложений

Guest — `labguest` с адресом `10.1.10.42`, Admin — `lab-admin` с `10.1.99.10`. Это пользователи сети; администраторская роль в тесте приложений не означает право управлять NGFW.

В «Континенте» пользователи входят через `auth.bks4.test`: шлюз связывает пользователя и его группы с IP. В Kerio используется автоматическая идентификация по IP. Для демонстрации роли работают с разных адресов.

Гостевой запрет Континента включает IRC, Jabber, BitTorrent и категории Chat/FileSharing. В Kerio AppID запрещает гостям приложения из категорий общения и передачи файлов. Администраторское исключение располагается выше гостевого запрета.

Проверяем свои IRC и BitTorrent на WAN-TEST: IRC — порты 6667/16667, BitTorrent — 6881/16881. Разные порты показывают, что решение основано на распознавании приложения. IRC проверяем командами printf и nc: ответ 001 подтверждает регистрацию. В Transmission администратор скачивает весь контрольный файл размером 3407872 байта; SHA256 сравниваем с исходным файлом на WAN-TEST. У гостя каталог загрузки остаётся пустым; запрет подтверждаем журналом NGFW. Одного успешного TCP-соединения для проверки приложения недостаточно.

У Континента веб-правила с AV стоят выше гостевого DPI; за ними — явный запрет остальных LAN→DMZ сервисов. Этот порядок позволяет проверять HTTP антивирусом и отдельно ограничивать приложения.

## 7. IDS/IPS и ложные срабатывания

IDS обнаруживает признаки атаки и пишет событие. IPS дополнительно блокирует соответствующий трафик. Сравниваем один тест в режиме журналирования и предотвращения: клиентская реакция должна совпадать с действием в журнале.

SID — идентификатор сигнатуры. В «Континенте» HOME_NET задаёт защищаемую DMZ `10.1.50.0/26`. Веб-сигнатуры ищут Nmap User-Agent, SQL-признаки и `/etc/passwd` в URI. Пользовательские SID 3900001/3900002 предназначены для SYN-потока и SYN-сканирования. Потеря XMAS-пакетов сама по себе не доказывает детект СОВ: их может отбросить МЭ раньше.

Kerio проверяет входящий WAN-путь. SSH-проба сопоставляется по SID 1:2001219: в Log определяется OpenSSH, в DropAndLog порт становится filtered, журнал содержит Packetdrop. Это проверка конкретной сигнатуры; по ней нельзя обещать блокировку любого сканирования.

Перед тестом Kerio нужно дождаться сообщения `Intrusion Prevention engine: Startup`. Прочитать журнал IPS и через 8 секунд проверить, что после Startup не появился Shutdown. Флаг enabled и успешное обновление базы не означают, что движок уже обрабатывает пакеты.

Прямой LAN→DMZ в Kerio имеет другую реакцию: тестовые веб-URI доходят до nginx и получают 404 без IPS-детекта; те же признаки из WAN блокируются. На защите объясняем область проверки и показываем обе реакции.

Ложное срабатывание — совпадение легитимного трафика с сигнатурой. В Континенте запрос документации `/docs?topic=/etc/passwd` попал под SID 4149401. Исключение разрешает обход IPS только для `10.1.99.10 → 192.168.100.2:8080`; оно охватывает этот сервис доверенного АРМ, а не один URI. Остальной WAN продолжает проверяться.

В Kerio IRC на нестандартном порту вызвал SID 1:2000345. Исключение этой сигнатуры глобальное. Также исключены информационные curl-SID 1:2002825/2013028. После исключения проверяют обе роли: администратор должен пройти, гостевой DPI — сохранить запрет.

## 8. GeoIP

GeoIP определяет страну по базе IP-префиксов. Для опыта WAN-TEST эмулирует источники `5.255.255.5` (RU) и `8.8.8.8` (US), обращаясь только к своей публикации `192.168.100.2:8080`. Это изолированный опыт с адресами источников.

При выключенном ограничении оба источника получают HTTP200. При включённом запрете US источник RU продолжает работать, US получает таймаут. В Континенте правило привязано к публикации DMZ; в Kerio действует глобальный фильтр входящего WAN.

GeoIP не устанавливает личность и физическое местоположение человека: VPN и прокси меняют видимый адрес, а база может ошибаться.

## 9. Журналы, уведомления и резервная копия

NGFW отправляют syslog на ADMIN-LINUX `10.1.99.10:514`. По записи разбираем время, источник, назначение, пользователя, правило или SID и действие. Таймаут клиента без соответствующего события может означать и проблему связи.

Внешний монитор на ADMIN-LINUX разбирает события IPS и AV и отправляет SNMP-уведомления приёмнику `10.1.99.10:162`. Это уведомления нашего монитора. Для проверки доставки сравнивается точный пейлоад отправителя и приёмника; обычный LinkUp не доказывает доставку сообщения об атаке.

Статистика группирует записи по правилам, сервисам, источникам и пользователям/приложениям. Число записей журнала не равно числу уникальных соединений: один поток может породить несколько событий.

Проверка backup/restore: создать штатную копию, изменить описание контрольного объекта, восстановить копию, сравнить описание и хеши конфигурации. Континент восстанавливает компонент CDC; Kerio — конфигурацию через Configuration.apply. Копии с паролями и сертификатами хранятся вне Git.

Экспорт PNETLab ZIP содержит топологию и ссылки на образы. Рабочие диски QEMU в него не входят, поэтому импорт ZIP не заменяет восстановление конфигурации NGFW.

## 10. Что показывать на защите

1. Топологию, четыре рабочие сети и одну включённую платформу. Объяснить роль OOB и общий адресный план.
2. Разрешённый HTTP из LAN и публикацию 8080/8443 из WAN; запрещённые SSH LAN→DMZ и DMZ→LAN; разрешённый SSH администратора.
3. Контрольный файл, EICAR и ZIP по HTTP; отдельно HTTPS и объяснение шифрования.
4. IRC/BitTorrent гостя и администратора на двух портах; показать пользователя и решение DPI в журнале.
5. Воздействие IDS/IPS с соответствующим SID/action, затем исключение ложного срабатывания и контроль сохранения защиты.
6. GeoIP off/on для RU/US; статистику, доставку уведомления и принцип проверки восстановления.

Перед переключением штатно выключить текущий NGFW и убедиться в его остановке. После запуска другой платформы проверить Management и привязки TAP; для Континента — вход пользователей в портал, для Kerio — готовность IPS. Команды для ввода в консоль — в [demo-checks.md](demo-checks.md).

## 11. Частые вопросы

**Почему сервер в DMZ?** Он доступен извне, но из его сегмента запрещено инициировать соединения в LAN. Это ограничивает последствия взлома сервера.

**Почему недостаточно закрыть порты мессенджера?** Приложение может работать на другом порту. Поэтому проверяем распознавание протокола на стандартном и нестандартном портах.

**Чем AV отличается от IPS?** AV ищет вредоносное содержимое файлов; IPS ищет признаки атак и нарушений протокола в трафике. Их решения и журналы проверяются отдельно.

**Почему EICAR проходит по HTTPS?** Без TLS-инспекции шлюз не видит содержимое зашифрованного ответа.

**Почему filtered ещё не доказывает работу IPS?** Пакет мог отбросить обычный МЭ или он мог потеряться. Нужны событие IPS с нужным SID и контроль разрешённого доступа.

**Почему исключение может быть опасным?** Оно уменьшает область проверки. Важно точно знать его границы: доверенный источник/сервис у Континента, глобальный SID у Kerio.

**Зачем тестировать восстановление?** Наличие архива не гарантирует, что его можно применить и получить нужную конфигурацию.

**Главное различие платформ в этой лабе?** Континент использует ЦУС, отдельную установку политики и ICAP-антивирус; Kerio объединяет управление в WebAdmin и имеет встроенный AV. В нашей схеме различается и область работы IPS.
